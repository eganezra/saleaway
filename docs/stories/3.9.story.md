# Story 3.9: Hide Blocked Stores for Launch

## Status

Done

## Story

**As the** operator,
**I want** the stores that block the pipeline hidden from the site and from the daily run, by a recorded and reversible decision,
**so that** the site launches with stores that work and no store is shown that nobody can check.

## Acceptance Criteria

1. A list of hidden stores is kept in the repository (`docs/data/hidden-stores.json`). The file records the date of the decision, and each entry has the store's slug and a reason code that is explained in the file, so a later fix knows which stores to cover. The first list is the 35 stores of run 16: the 34 that answered 403 or 429, and the other listing on the same website as one of them (`ackermans-baby-kids-toys`).
2. A documented operator command hides every store on the list in the local or the live database, and the same command with `--undo` makes them visible again. It can be run twice with the same result, it changes nothing else, and it checks its input before writing (FR3).
3. A hidden store is not fetched by the daily run and is not shown on the site. The other 57 stores and all 10 categories are unaffected. Re-running the retailer seed does not undo it.
4. An operator can still fetch one hidden store with `POST /admin/run?store=<slug>`, so a store can be tested again before it is shown.
5. The command is run on the live database, and the live home page shows 57 store cards and none of the 35 hidden ones (the page is not cached yet; see "Live run").
6. The README explains how to hide and restore stores, and that blocking can change from day to day.

### The list (`docs/data/hidden-stores.json`)

Already in the repository (written by the SM). Shape:

```json
{
  "decidedOn": "2026-10-30",
  "source": "text: where the decision comes from",
  "reasons": { "http_403": "text", "http_429": "text", "same_site_as_blocked": "text" },
  "stores": [ { "slug": "ackermans", "reason": "http_429" } ]
}
```

`parseHiddenStores(value: unknown): HiddenStores` (new, `packages/core/src/hidden-stores.ts`, **pure**: no file access, no clock, no SQL; the ops script reads the file and passes the parsed JSON in) returns `{ decidedOn: string; source: string; reasons: Record<string, string>; stores: Array<{ slug: string; reason: string }> }` or **throws one `Error` that names every problem it finds** (not only the first: `buildSeed` in `packages/core/src/seed.ts` stops at the first one, and this list is short enough to report all of them). It rejects:

- a value that is not an object, or with a missing or wrongly typed field;
- `decidedOn` that is not a real calendar date `YYYY-MM-DD`;
- `stores` empty, or with more than 200 entries (a sanity limit);
- a slug that does not match `^[a-z0-9-]+$` (the same rule as the seed), or is longer than 100 characters;
- a duplicate slug;
- a `reason` that is not a key of `reasons`, and a `reasons` key that does not match `^[a-z0-9_]+$`;
- text fields longer than 500 characters or containing a control character.

The checks that need the database or the seed file (does each slug exist?) are **not** in the pure function: the test reads `docs/data/retailers-seed.tsv` for the committed list, and the command checks the database (see below).

**Live check in Task 1** (read only): `SELECT slug, is_visible FROM retailers WHERE slug IN (<the 35 slugs, quoted by sqlString>)` against the live database must return 35 rows, all `is_visible = 1`; and `SELECT COUNT(*) FROM retailers WHERE is_visible = 1` must be 92. If not, **stop and tell the user** (someone changed the data). ### The command (`pnpm ops:hide`)

`scripts/ops/src/hide.ts`, built the way `seed.ts` is built: read the files, check everything **before anything is written**, write SQL to a temporary file outside the repository, run it with `wrangler d1 execute saleaway --file ... --local|--remote` from the web app's folder (so the local database is the copy `pnpm dev` reads), delete the file, then **ask the database whether the change really happened** (Wrangler exits 0 when the operator answers "no" at its confirmation prompt, the lesson of Story 1.3). Log with the ops logger (`log.ts`), never `console.log`.

- **Arguments (`parseHideArgs` in `args.ts`, pure):** exactly one of `--local` or `--remote` (no default, so the live database is never written by accident); optionally `--undo`; optionally `--slug <slug>` (can be given more than once) to limit the command to some stores **that are on the list** (a slug that is not on the list is an error, so this command can never be used to hide or show an arbitrary store). Any other argument, or `--slug` without a value, or a slug that is not `^[a-z0-9-]+$`, is a usage error that writes nothing. Usage text: `Usage: pnpm ops:hide --local | --remote [--undo] [--slug <slug> ...]`.
- **SQL (`buildVisibilitySql(slugs: string[], visible: 0 | 1)` in `sql.ts`):** one statement, `UPDATE retailers SET is_visible = <0|1>, updated_at = strftime('%Y-%m-%dT%H:%M:%SZ','now') WHERE slug IN ('a', 'b', ...);`, with every slug passed through `sqlString` (quotes doubled, control characters rejected) and the 0 or 1 through `sqlInt`. An empty list throws. It touches **only** `is_visible` and `updated_at`, and only the named slugs.
- **Hiding** sets `is_visible = 0` for the selected slugs; **`--undo`** sets `is_visible = 1` for them. Running either twice gives the same result. `--undo` shows every selected store, **including one that an operator had hidden for another reason**; the README says so.
- **Check afterwards (`--json` query, like `seededCounts` in `seed.ts`):** `SELECT COUNT(*) AS selected, SUM(is_visible) AS visible FROM retailers WHERE slug IN (...)` and `SELECT COUNT(*) AS visible FROM retailers WHERE is_visible = 1`. Hiding must leave `selected` = the number of slugs and `visible` = 0 among them; `--undo` must leave all of them visible. If the numbers are wrong, or a slug on the list is not in the database (`selected` is smaller than the list), log `hide_not_applied` with the numbers found and exit 1. On success log `hide_done` (`target`, `action`, `stores`, `visibleTotal`) and exit 0.
- **No `--yes` for `--remote`**: in a terminal Wrangler asks before it writes to the live database, as for the seed.
- **Free-tier impact (note required by the coding standards):** one `UPDATE` of at most 35 rows and a few reads, once. Nothing runs on a schedule.

[Source: docs/stories/1.3.story.md (ops:seed design); architecture/coding-standards.md#critical-fullstack-rules ("Safe SQL in the operator CLI"); architecture/unified-project-structure.md (`scripts/ops`)]

### Gaps and decisions for the developer to note

1. **A recorded list, not a rule.** Blocking is not stable (the 429s especially). The list is the user's decision of 2026-10-30, taken from run 16, and nothing hides or shows a store automatically.
2. **The reason lives in the repository file, not in the database.** A `hidden_reason` column would be a migration for information the operator reads in one file. Story 4.1 (override command) and Story 4.2 (health report) may decide differently.
3. **`ackermans-baby-kids-toys` (35th store)** is an SM judgement (same website as a store that answered 429). The user can drop it from the list before the Dev starts.
4. **Hiding by `is_visible` is deliberate, instead of an override with a hide flag.** An override hide (Story 4.1) only hides a store on the site; the pipeline would still fetch it every night, which is exactly what we want to stop for a store that blocks us. The two stay separate. **For the PO:** Story 4.1 AC1 says the override command can "hide or show a store"; it must not be confused with this flag.
5. **A hidden store can still be fetched by hand** (Task 4), which changes Story 3.2's rule that `?store=` finds only stores a normal run would process.
6. **`--undo` shows every listed store**, even one that had been hidden for another reason. It is documented, not prevented.
7. **PRD follow-ups (done by the PO's correct-course on 2026-10-30, `docs/change-proposals/2026-10-30-blocked-stores.md`):** Story 3.8's trigger, Story 3.6 criterion 3, Story 3.4 criterion 7 and 8, Story 4.1 (criterion 8), Story 4.3 (criterion 6), Story 4.5, the domain text and the new Story 5.4 were updated. Nothing in this story's scope changed.
8. **The remaining 57 are not all "working":** the 3 `manual` stores have no data until Story 4.1, and `benji-moon` is an `error` until its address is fixed (Story 4.3). The home page keeps showing every visible store as "On sale" until Epic 3 reads real discounts; this story does not change that.
9. **Showing a hidden store again is not the same as fixing it.** `pnpm ops:hide --undo --slug <slug>` only sets `is_visible = 1`. The store keeps its `html` or `shopify_json` method, so the nightly run fetches it again, and a store that still blocks would be blocked again. Use `--undo` only for a store that has just been re-tested and answered (`POST /admin/run?store=<slug>`). To show a store that still blocks with hand-entered values, use the `manual` method and an override (Story 4.1, criterion 8, and Story 5.4). The README says this.
