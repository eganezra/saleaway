## Status

## Story

**As the** operator,
**I want** pages fetched politely and results classified,
**so that** I know what happened with each store.

## Acceptance Criteria

1. Requests use a clear user-agent with a contact address, a timeout, and a limited number of redirects (FR5, NFR6).
2. robots.txt is checked and respected.
3. Each result is classified as OK, blocked, not found, redirected away, JavaScript-only, or error (FR6).
4. The fetcher is tested from a deployed Worker, not only from a laptop, and the per-store results are saved to `docs/fetch-spike.md` as a follow-up table.
5. No attempt is made to evade bot protection or solve challenges (NFR6).
6. CPU time per store is measured on the deployed Worker for at least Bash, Woolworths, Takealot and one Shopify store (fetch, classify, validate and extract). If any store regularly exceeds 8 ms of CPU **[Assumption]**, the result and the chosen response are recorded: a streaming parse, the `manual` method for that store, or Story 3.8 (fallback runner).

### Politeness and safety rules (these are requirements, not suggestions)

- **One page request per store per run**, plus one `robots.txt` request per store per run, and the runs are staggered 15 seconds apart. At most 3 redirect hops per request.
- **User-agent, on every request including `robots.txt`:** `SaleawayBot/1.0 (+https://saleaway.online/contact)` (the domain the user registered on 2026-10-30; the first draft said `.co.za`). The contact page does not exist until Stories 2.5 and 4.4; the user knows this and accepts it for now.
- **Only `https`.** A redirect to `http://` is never followed. No credentials in a URL, no port other than 443.
- **No attempt to evade bot protection (NFR6):** no spoofed or rotated user-agent, no extra headers made up to look like a browser, no cookies, no retries after a `blocked` result, no solving of challenge pages, no proxies. A blocked store is recorded as blocked, and an operator decides what to do (usually the `manual` method).
- **A `manual` store is never fetched**, not even `robots.txt`.
- Never store retailer content (NFR7): the page body is not saved. This story reads no body except in the measurement probe, and the probe keeps only counts.

### Core rules (`packages/core`, pure, tested)

File names follow the architecture's tree (`url-safety.ts`, `classify.ts`) plus `robots.ts`.

**`url-safety.ts`**

- `isSafeFetchUrl(value: string): boolean`: true only when the value parses as a URL with protocol `https:`, no username or password, port empty or `443`, a host name (**after removing one trailing dot**, so that `localhost.` is treated as `localhost` and `x.internal.` as `x.internal`) that contains a dot and is not `localhost` or a name ending in `.localhost`, `.local` or `.internal`, **not an IP address of any kind** (no dotted-quad IPv4 after URL normalisation, which also turns `http://2130706433/` into `127.0.0.1`, and no IPv6 literal in square brackets), and a total length of at most 2048 characters. This is stricter than the architecture's "reject localhost, private and link-local addresses" because a Worker cannot resolve a name to see its address, and no retailer in the seed uses an IP address.
- `resolveRedirect(current: string, location: string): string | null`: resolves a `Location` value (absolute or relative) against the current URL and returns the result **only if** `isSafeFetchUrl` accepts it; otherwise `null` (an `http://` target, an IP address, an unparsable value).

**`classify.ts`**

- `classifyResponse(outcome): FetchClass`, where `outcome` is `{ status: number | null; failed: boolean; redirectedAway: boolean; knownJsShell: boolean }`. Rules, in this order:
  1. `failed` (the request threw, timed out, or was refused) or `status` is `null`: **`error`**.
  2. `401`, `403`, `429`, `503`: **`blocked`**.
  3. `404`, `410`: **`not_found`**.
  4. Any other status of 500 or more: **`error`**. Any other status below 200 or from 300 to 499 (a redirect that was not followed, a `400`, a `405`, a `451`): **`error`**.
  5. A status from 200 to 299: **`redirected_away`** if `redirectedAway` is true; else **`js_only`** if `knownJsShell` is true; else **`ok`**.
- `redirectedAway(expectedUrl: string, finalUrl: string): boolean`: true when the final host differs from the expected host after removing a leading `www.` from both, **or** when the final path is `/` (or empty) while the expected path is not `/`. A redirect to another path on the same host (for example `/outlet` to `/collections/outlet`) is **not** "away".

**`robots.ts`**

- `isAllowedByRobots(robotsTxt: string, pathAndQuery: string, agent = 'SaleawayBot'): boolean`, following RFC 9309: lines are `field: value` with `#` comments; a group is one or more `User-agent` lines followed by `Allow` and `Disallow` rules; **use the group whose `User-agent` value matches `agent` case-insensitively as a whole product token, and only when there is none, the `*` group; if several groups match, combine their rules into one; if neither exists, everything is allowed.** In the chosen group, a rule matches when its pattern matches the start of `pathAndQuery` (`*` matches any run of characters, a trailing `$` anchors the end); **the longest matching pattern wins, and `Allow` wins a tie**; no matching rule means allowed; an empty `Disallow` allows everything. Ignore every other directive (`Sitemap`, `Crawl-delay`, ...) and any line that is not understood. Accept CRLF and a leading byte order mark. Only the first 500 KiB of the text are considered (the caller also limits what it reads).

[Source: architecture/coding-standards.md#critical-fullstack-rules (shared logic in core, no I/O, fixture tests); architecture/unified-project-structure.md (`url-safety.ts`, `classify.ts`); architecture/error-handling-strategy.md#backend-error-handling (`classifyFetch`); architecture/core-workflows.md#state-rules-per-fetch-result; architecture/security-and-performance.md; RFC 9309 (the robots exclusion protocol), outside the architecture docs]

### The fetcher (`apps/pipeline/src/fetcher.ts`)

`fetchPage(url, fetchFn, options?)` returns `{ ok: true, status, finalUrl, hops, response }` or `{ ok: false, reason }`. Behaviour:

1. If `isSafeFetchUrl(url)` is false: `{ ok: false, reason: 'unsafe_url' }` and **no request is made**.
2. Request with `redirect: 'manual'` (Cloudflare returns the real 3xx response with its `Location` header, checked by the SM on 2026-10-29), the user-agent above and an `Accept` header (`text/html,application/xhtml+xml,application/json;q=0.9,*/*;q=0.8`), and **no other headers**, with `signal: AbortSignal.timeout(FETCH_TIMEOUT_MS)`. `FETCH_TIMEOUT_MS` is **10,000** **[Assumption: no document sets it; 10 seconds per request keeps one store far inside the 15 minute consumer limit]**.
3. If the status is 301, 302, 303, 307 or 308 with a `Location` header: resolve it with `resolveRedirect`. A `null` result gives `{ ok: false, reason: 'unsafe_redirect' }` (never followed). More than **3** hops gives `{ ok: false, reason: 'too_many_redirects' }`. A redirect status without a `Location` gives `{ ok: false, reason: 'bad_redirect' }`. Cancel the unread body of every intermediate response (`await response.body?.cancel()`) so connections are freed.
4. A request that throws (a timeout is a `TimeoutError`, a refused connection or a TLS failure is a `TypeError`) gives `{ ok: false, reason: 'timeout' }` or `{ ok: false, reason: 'network' }`.
5. Any other status ends the loop: return `{ ok: true, status, finalUrl, hops, response }` with the body **unread**. The caller decides whether to read it.

The same function fetches `robots.txt`. Subrequests per store: at most one `robots.txt` (with up to 3 hops) and one page (with up to 3 hops), so at most 8, far inside the 50 a Free invocation allows. [Source: architecture/external-apis.md#retailer-sale-pages-public-websites; architecture/security-and-performance.md; architecture/verified-platform-limits-cloudflare-free-plan-checked-2026-10-29.md (50 subrequests per invocation)]

### The robots check (`apps/pipeline/src/robots.ts`)

`checkRobots(origin, pathAndQuery, fetchFn)` returns `'allowed'`, `'disallowed'` or `'unreachable'`:

- Fetch `${origin}/robots.txt` with `fetchPage`. Read at most **500 KiB** of the body (cancel the rest).
- **2xx**: parse with `isAllowedByRobots` and return `allowed` or `disallowed`.
- **4xx, including 403 and 404** ("the file is unavailable", RFC 9309): `allowed`.
- **5xx, a timeout, a network failure, an unsafe or endless redirect** ("unreachable"): `unreachable`. RFC 9309 says to assume the whole site is disallowed in this case, so the page is **not** fetched.
- No caching in this story (one `robots.txt` request per store per run; 79 different sites serve the 92 stores, so a site with several listings is asked a few times a day at most).

[Source: architecture/external-apis.md ("`GET {origin}/robots.txt` - checked before the page fetch"); prd/requirements.md#fr5, #nfr6; RFC 9309]

### Per-store processing (`process-store.ts`)

Replace the placeholder with this flow. Each step ends the function with one `saveRunResult`:

1. Read the retailer (`id`, `slug`, `extractionMethod`, `saleUrl`, `seedStatus`). Not found: log `retailer_not_found` and write nothing (unchanged).
2. `extractionMethod` is `manual`: record `skipped_manual` and **stop** (nothing is fetched).
3. `saleUrl` missing or not safe: record `error` with the text `unsafe_url`.
4. `checkRobots(origin, path + search)`: `disallowed` records **`blocked`** with the text `robots_disallow`; `unreachable` records **`error`** with `robots_unreachable`. In both cases the page is not fetched.
5. `fetchPage(saleUrl)`. A failure records `error` with its reason (`timeout`, `network`, `too_many_redirects`, `unsafe_redirect`, `bad_redirect`, `unsafe_url`).
6. Otherwise classify with `classifyResponse({ status, failed: false, redirectedAway: redirectedAway(saleUrl, finalUrl), knownJsShell: seedStatus === 'verified_js_shell' })`. Record the class, the final `http_status`, and for a class other than `ok` and `js_only` the text `http_<status>` (for example `http_403`) or `redirected_to_<host>`.
7. Unless the measurement probe is on, **cancel the body without reading it** (`await response.body?.cancel()`).
8. `duration_ms` is the time the whole step took (two calls of the injected clock). `discount_percent` stays null. **No `sale_records` or `overrides` write.**

**`js_only` rule (SM decision):** a store whose `seed_status` is `verified_js_shell` (19 of the 92 today: the spreadsheet recorded that the page loads but its products appear with JavaScript) is classified `js_only` on a 2xx answer without reading the page. This also saves CPU, because those pages can only ever be URL-verified (Story 3.3, criterion 5). For every other store a 2xx answer is `ok`. Story 3.3 may add a body-based check for a store that turns into a JavaScript shell later.

**The sale URL comes from `retailers.sale_url` only.** An active override's sale URL replaces it from Stories 2.3 and 3.5 onward. ### Single-store runs

Manual runs fetch every store again, which breaks the one-page-per-store-per-day rule (Story 3.1, decision 7). So `POST /admin/run` accepts an optional query parameter `store=<slug>`:

- The slug must match `^[a-z0-9-]+$`; anything else gives `400` with the error JSON `code: "bad_store"`.
- The slug must belong to a store that would be part of a normal run (visible, with an `https://` sale URL); otherwise `404` with `code: "store_not_found"`.
- It creates a run with `trigger` `manual` and `stores_total` 1, and enqueues one message (delay 0). The response is `{ ok: true, runId, storesTotal: 1 }`.
- The token check and the paused check come **first**, exactly as today.
- `startRun` takes an optional `retailerId`; without it nothing changes. The close cron closes these runs like any other.

### The CPU probe (`apps/pipeline/src/probe.ts`, measurement only)

The CPU limit applies to work, not to waiting for the network. To learn how much CPU the later validation and extraction steps will need on real pages, before they exist, this story adds a **stand-in** that does representative work on the real page. It runs **only** when the variable `MEASURE_CPU` is exactly `true` (the committed value is `"false"`), only for a 2xx answer, and keeps only counts:

- **HTML pages:** stream the response body through one `HTMLRewriter` pass with a handful of selectors that count matches (for example `a`, `script`, `span`, `[class*="price"]`, `script[type="application/ld+json"]`), and count the bytes.
- **Shopify stores (`extraction_method` `shopify_json`):** additionally request `<sale_url>/products.json?limit=250` (build it with the `URL` API: append `/products.json` to the path and set `limit=250`, dropping any existing query; same user-agent, same rules, one extra request, measurement runs only), parse it with `JSON.parse`, and count the products and variants that have a compare-at price.
- Log one line `cpu_probe` with the store `slug`, the byte counts and the counts found (fields `slug`, `bytes`, `anchors`, ... never `message`, `level` or `time`) so the `wrangler tail` line can be matched to the store.
- **`HTMLRewriter` exists only in the Workers runtime, not in Node, where Vitest runs** (the PO checked: `typeof HTMLRewriter` is `undefined` there). `probe.ts` therefore takes the rewriter as a parameter (a factory, `() => new HTMLRewriter()` in production), so the tests can pass a small fake. The real `HTMLRewriter` path is proven by the local check (Task 8) and the live `cpu_probe` lines (Task 9), which must show counts above zero.
- It never stores or logs any page text, and it is not part of the normal path. Stories 3.3 and 3.4 replace it with the real steps, and the CPU measurement must then be **repeated** with the real code (a note for the SM to add to Story 3.4).

### Gaps and decisions for the developer to note

1. **`js_only` is decided from `seed_status`, not from the page.** The PRD lists `js_only` among the classes but does not say how a Worker should detect it. Using the spreadsheet's `verified_js_shell` flag (19 stores) needs no body parsing and saves CPU. A store that later turns into a JavaScript shell is not detected until Story 3.3.
2. **A robots refusal is recorded as `blocked`** (with the text `robots_disallow`), and an unreachable `robots.txt` as `error` (`robots_unreachable`), following RFC 9309. Both keep the last good sale record (core-workflows, "blocked, error"). A 4xx for `robots.txt` means "allowed".
3. **Other status rules:** 401 is `blocked`; every other status that is not 2xx, 403, 404, 410, 429, 503 is `error`.
4. **`redirectedAway` is deliberately simple:** another host (ignoring `www.`), or the home page. Search pages, login pages and challenge pages are Story 3.3.
5. **Stricter URL safety than the docs:** every IP literal and every single-label host is rejected.
6. **The 10 second timeout is an assumption** (no document sets one).
7. **Single-store runs** are added to `/admin/run` (it resolves Story 3.1's open question about manual runs and politeness).
8. **The CPU probe is a stand-in** for steps that do not exist yet, so criterion 6 ("fetch, classify, validate and extract") is met with an upper-bound stand-in and must be **repeated after Story 3.4**. This is the first of two gates: this story answers "does fetching and parsing a real page fit", Story 3.4 answers "does the real extraction fit". **PO ruling (Sarah, 2026-10-29):** the stand-in satisfies criterion 6 for this story, and a new criterion 8 was added to Story 3.4 in the PRD to repeat the measurement with the real code.
9. **Politeness exceptions, all one-off and known to the user:** 3 measurement fetches for 4 stores, and the manual full run followed hours later by the first nightly cron.
10. **Duplicate URLs:** `woolworths-all-depts` and `woolworths-fashion` have exactly the same sale URL, so it is fetched twice in a run. Several other sites have more than one listing too (`bash.com` 4, `woolworths.co.za` 3, ten sites in all), spread out by the 15 second stagger. Accepted; a per-run URL cache is a later optimisation.
11. **The user-agent's contact URL does not exist yet** (the site is not on its domain; the contact page is Story 2.5). A retailer who looks it up will find nothing until launch. This must be fixed before the site is announced.
12. **Rolling back:** the pipeline can be paused with `PIPELINE_ENABLED` false, and `wrangler rollback` returns the previous version (the placeholder), if the fetcher misbehaves live.

### Refactoring Performed

- **File**: `packages/core/src/robots.ts`
  - **Change**: added a work budget (`MAX_STEPS`, 5 million steps) to the wildcard matcher. If a `robots.txt` costs more than the budget to evaluate, `isAllowedByRobots` answers "not allowed" and stops.
  - **Why**: the Dev capped the rule count (2000) and the pattern length (1024), but the cost is rules x pattern length x text length. I measured a hostile file (2000 rules of 1000 characters, many `*`) at **25 seconds of CPU** for one question. Any retailer's `robots.txt` is outside our control, and this runs in the consumer of every store. A real file (400 wildcard rules) takes 0.4 ms.
  - **How**: the matcher now counts the work it does. A real file never gets close to the limit (a file of 2000 wildcard rules still evaluates in full: tested). A file that exceeds it is not trusted, so the page is not fetched, which is the polite default. The worst case is now about 100 ms.
- **Tests added** (all five surviving mutations are now killed; the new tests were mutation-checked again):
  - `packages/core/tests/robots.test.ts`: hostile file is "not allowed" within a second; a large ordinary file is still read in full.
  - `apps/pipeline/tests/fetcher.test.ts`: an `AbortError` is reported as `timeout`; the body of every intermediate redirect is cancelled and never read (this was in the story's test list, but was not tested).
  - `apps/pipeline/tests/robots.test.ts`: an endless body is read only up to 500 KiB and then freed (a stream that counts reads); text beyond the cap in one chunk is not used (this was in the story's test list, but the existing test also passed with the cap removed, because the core parser has its own cap).
  - `apps/pipeline/tests/probe.test.ts`: variants with no compare-at price, or an empty one, are not counted.
- **Equivalent mutant, left alone:** removing `.subarray(0, maxBytes)` in `apps/pipeline/src/robots.ts` changes nothing, because `packages/core/src/robots.ts` cuts the text at 500 KiB too. Two layers is fine for a limit that protects CPU.
