# Story 3.3: Sale Page Validation

## Status

Done

## Story

**As a** bargain hunter,
**I want** only real sales shown,
**so that** I can trust Saleaway.

## Acceptance Criteria

1. A page passes validation only when it shows discounted products, for example was/now prices, percentage-off labels or discount badges (FR7).
2. An error page, a redirect to the home page, a login or challenge page, or an empty listing fails validation.
3. Validation is a pure function with unit tests using saved page samples from at least 5 different stores (NFR12).
4. A failing validation marks the sale ended (FR10), except a challenge or login page, which is treated like a blocked fetch and keeps the last good record.
5. A page whose products load with JavaScript is recorded as URL-verified only, not content-verified, and shown as "On sale" (FR7).
6. Test samples are trimmed to the minimum markup needed (a few KB), not whole retailer pages (NFR7).

### The rules (`packages/core/src/validate.ts`)

Everything here except the signatures is the SM's design from the PRD's words (FR7, AC1 and AC2); thresholds are **[Assumption]** and are meant to be tuned on the samples (Task 3), as long as every rule still reads as one sentence. A verdict is judged on **positive evidence only**: a page is called "not a sale" only when something on it says so. When the page cannot be judged, the answer is "unverifiable", which keeps the store shown as "On sale" and is the safe side (FR7).

```typescript
export type ValidationVerdict = 'valid' | 'ended' | 'blocked' | 'unverifiable';
export type ValidationReason =
  | 'discounts_found'                              // valid
  | 'redirected_away' | 'error_page' | 'empty_listing' | 'no_discounts'   // ended
  | 'challenge_page' | 'login_page'                // blocked
  | 'javascript_shell' | 'unreadable';             // unverifiable
export interface ValidationSignals {
  amounts: number;          // price-like amounts found, for example "R 1 299.00" or "R199"
  percentLabels: number;    // "30% off", "save 25%", "-40%" style labels or badges
  wasPrices: number;        // was/now pairs: strike-through or "was" prices next to an amount
  structured: number;       // structured-data hints: JSON-LD offers with a higher "was" price, `compare_at_price` values that are not null
  scripts: number;          // <script> tags
  textLength: number;       // visible text length after removing tags, scripts and styles
}
export interface ValidationResult { verdict: ValidationVerdict; reason: ValidationReason; signals: ValidationSignals }
export interface PageInput { text: string; expectedUrl: string; finalUrl: string; truncated: boolean }
export function validateSalePage(page: PageInput): ValidationResult;
export function recordEffect(verdict: ValidationVerdict): { state: 'active' | 'ended' | null; validation: 'content_verified' | 'url_verified' | null };
```

`validateSalePage` applies these rules **in this order**; the first that matches decides:

1. **`ended` / `redirected_away`:** `redirectedAway(expectedUrl, finalUrl)` (already in core, Story 3.2) is true. (The fetcher already reports a redirect to another site or to the home page as the class `redirected_away`; this repeats the rule so the function is complete on its own.)
2. **`blocked` / `challenge_page`:** the `<title>` or the first 4 KiB of the text contains a bot-challenge marker, matched case-insensitively: "just a moment", "attention required", "checking your browser", "access denied", "pardon our interruption", "verify you are human", "captcha". A challenge page is the same thing as a block, so it must **not** end the sale (see `recordEffect`).
3. **`blocked` / `login_page`:** the `<title>` matches "sign in", "log in" or "login", **and** the page has a password field (`type="password"`), **and** `amounts` is under 3.
4. **`ended` / `error_page`:** the `<title>` or the first `<h1>` matches (as whole words, case-insensitive) "404", "not found", "page not found", "no longer available", "oops", "error" or "something went wrong", **and** `amounts` is under 3 **and** there are no discount signals.
5. **Signals** are counted over the whole text (bounded, see "Size and safety"): `percentLabels`, `wasPrices`, `structured`. **`valid` / `discounts_found`** when `percentLabels + wasPrices + structured` is **at least 2** **[Assumption: one stray "% off" in a footer must not make a sale]** **and** `amounts` is at least 2.
6. **`unverifiable` / `javascript_shell`:** there is no valid discount (rule 5 failed) and the page looks like an unrendered application: `amounts` under 3 and (a root container such as `<div id="root">`, `<div id="app">`, `<div id="__next">` or `<app-root>`, or a `<noscript>` text asking to enable JavaScript, or `scripts` at least 8 with `textLength` under 1500).
7. **`ended` / `empty_listing`:** the page was **not truncated**, no valid discount, `amounts` under 3, and the text says there is nothing ("no products", "0 results", "nothing found", "no items", "no results", "sorry, we couldn't find"), case-insensitive.
8. **`ended` / `no_discounts`:** the page was **not truncated**, no valid discount, `amounts` at least 3 (the page lists priced products) and no discount signal at all.
9. **`unverifiable` / `unreadable`:** anything else (a few discount signals but not enough, or no recognisable content), **including every truncated page that did not reach `valid`, `blocked` or `javascript_shell`** (the page was cut at the size limit, so the missing part may hold the discounts; rules 7 and 8 therefore never fire on a truncated page).

`recordEffect(verdict)` is the rule for "what the sale record becomes", applied by Story 3.5 (core-workflows, "State rules per fetch result"): `valid` gives `{ state: 'active', validation: 'content_verified' }`; `ended` gives `{ state: 'ended', validation: null }`; **`blocked` gives `{ state: null, validation: null }`** (keep the last good record, as for a blocked fetch); `unverifiable` gives `{ state: 'active', validation: 'url_verified' }` (shown as "On sale", AC5).

**Decisions flagged for the PO:** (a) AC2 says a challenge or login page "fails validation" and AC4 says a failing validation "marks the sale ended"; the SM's design makes challenge and login pages `blocked` (keep the last good record) because ending a sale because a retailer showed a robot check for one night would hide a good store, contrary to the state table in `core-workflows.md` ("blocked, error: last good record kept"). (b) AC4's marking is implemented here as `recordEffect` and **applied in Story 3.5**; no `sale_records` write happens in this story. [Source: prd/requirements.md#fr7, #fr10; architecture/core-workflows.md#state-rules-per-fetch-result; docs/stories/3.2.story.md (`redirectedAway`)]

### Size and safety

- **Work is bounded:** `validateSalePage` must scan the text a fixed number of times with patterns that cannot backtrack badly (no nested quantifiers on the same characters; use the `matchAll` with global patterns, linear in the text). A test feeds it a 3 MiB page of hostile text (long runs of digits, spaces, `<` characters and `R` characters) and it must finish in under 1 second.
- **The pipeline reads at most 3 MiB** of a page **[Assumption: Woolworths, the largest seen, was 1.6 MB]**. `readLimited(response, maxBytes)` returns `{ text, bytes, truncated }` (`bytes` is the number of bytes read), or `null` when the read fails (as today: `checkRobots` treats `null` as unreachable); a page longer than the limit is cut, `truncated` is true, and the rest is never read. `checkRobots` uses `.text` and ignores `bytes` and `truncated`.
- **No retailer content is kept** (NFR7): the function returns counts and a verdict, never text. The log line carries counts and the verdict only.

[Source: architecture/coding-standards.md#critical-fullstack-rules; prd/requirements.md#nfr7]

### The pipeline step (`apps/pipeline/src/process-store.ts`)

After the fetch and the classification, **only when** the class is `ok` **and** `MEASURE_CPU` is not `"true"`:

1. Read the body with `readLimited(page.response, MAX_PAGE_BYTES)` (`MAX_PAGE_BYTES = 3 * 1024 * 1024` in `fetcher.ts`). If the read fails (a timeout while streaming), log `page_read_failed` (field `slug`) and continue as if there were no verdict; the class and the `run_results` row stay as they are.
2. Call `(deps.validate ?? validateSalePage)({ text, expectedUrl: saleUrl, finalUrl: page.finalUrl, truncated })`. `Deps` (in `types.ts`) gets an **optional** field `validate?: (page: PageInput) => ValidationResult`, which production does not set (so the real function runs) and tests set to a stub, for example one that throws.
3. Log one line `page_validated` with the fields `slug`, `verdict`, `reason`, `bytes`, `truncated` and the six signal counts (`amounts`, `percentLabels`, `wasPrices`, `structured`, `scripts`, `textLength`): numbers and short words only, **never any page text**. About 57 lines a day, far inside the free log allowance.
4. Put the result in the function's `Outcome` (new optional field `validation`) so Story 3.5 can save it. **Nothing is written to the database for it in this story**, and the `run_results` class and error text do not change.
5. For class `js_only` (and every class other than `ok`) the body is still cancelled unread, as today. For `MEASURE_CPU` `"true"` the probe runs as today and validation does not.
6. **Validation must never throw out of the store job** (coding standards): wrap steps 1 and 2 in a `try`/`catch` that logs `validation_failed` (`slug`, `err`) and continues.

The request count and the one-page-per-store rule do not change (no new request). [Source: architecture/backend-architecture.md (`process-store.ts`: robots, fetch, classify, validate, extract, save); architecture/coding-standards.md#critical-fullstack-rules]

### Gaps and decisions for the developer to note

1. **Four verdicts, not two** (valid, ended, blocked, unverifiable): the PRD's "passes or fails" cannot express "cannot be judged" (AC5) or "a robot check, not a missing sale" (core-workflows). The SM's design; flagged for the PO.
2. **Nothing is saved here.** AC4 is the pure `recordEffect`; Story 3.5 applies it. **For the PO:** AC4 here and AC2 of Story 3.5 overlap and should be read together.
3. **Thresholds are assumptions** (2 discount signals and 2 amounts for `valid`; 3 amounts for "lists products"; 3 MiB; 16 KiB per sample) to be tuned on the samples. The Dev records the final numbers.
4. **The samples are fetched once from the Dev's computer, not the Worker,** so a page may differ slightly from what the Worker sees (a different network may be shown a different page). Story 3.6's first full run will show the real verdicts for all 57 visible stores; stores whose verdict looks wrong then get a new sample.
5. **Pages the spreadsheet says are JavaScript shells (`js_only`) are not read at all.** The content-based `javascript_shell` verdict exists for the others (for example a single-page application that was classified `ok`).
6. **A store the fetcher classified `ok` can now be judged `ended`** in the log, but the site does not change until Story 3.5 and the web deploy (Story 2.3's hazard).
7. **Reading the body costs CPU and memory** on the Worker (up to 3 MiB as text per store). Story 3.4, criterion 8 re-measures the real cost.

### Code Quality Assessment

The design is sound and reads well: one pure function, rules in the stated order, positive evidence only, and `recordEffect` as a small table. The pipeline step is correctly narrow (only an `ok` page is read, every failure is logged and contained, nothing is saved). The samples are real, small and clean: I checked every file for retailer text, and the only words left are page titles, the placeholder `Product N`, and generic labels; the only address anywhere is the `schema.org` offer type, and all `src` attributes are local `/static/N.js` placeholders (NFR7 met).

**I found two real defects by running the validator on inputs the Dev did not tune it on. Both are fixed.**

1. **A hang: the scan was quadratic on a page with many `<script>` blocks and no `<style>` (or the other way round).** `removeBlocks` searched for both `<script` and `<style` from the current position on every pass, so a tag that does not exist was searched for to the end of the page once per block of the other kind. A 3 MiB page of `<script></script>` (185,000 blocks) **did not finish in 10 minutes**; I stopped it. The Dev's hostile-input tests used unclosed tags (which stop the loop at once) and so never hit it. Why it matters: the queue consumer's CPU is not capped, so one such page would hold a consumer until the 15 minute wall-time limit, and with `max_concurrency` 2 it could stall the run. Real retailers do not serve such a page, but a broken or hostile one is exactly what the "bounded work" requirement exists for. **Fix:** the next position of each tag is remembered and looked up again only after it has been passed, so the total work is linear. The same 3 MiB pages now take 17 to 94 ms. Five hostile-input tests were added (closed scripts, closed styles, both, comments, many small tags).
2. **A false "challenge" on a real sale page.** The body marker rule matched "captcha" or "access denied" anywhere in the first 4 KiB of text, so a genuine sale page with a "protected by reCAPTCHA" notice near its top came out as `blocked`. A store that is judged `blocked` never gets a first validation, so it would go stale 72 hours after it was added and disappear (Story 2.3). **Fix:** a marker in the **title** is always a challenge; a marker in the **body** counts only when the page lists fewer than three prices (a challenge page has no products). Tests for both directions were added, and the paragraph in `core-workflows.md` (shard and monolith) now says so. This narrows the story's rule 2 text ("the title or the first 4 KiB of the text"); Bob and Sarah should read it with this review.

**Mutation testing, on a throwaway clone (your working tree was not touched by it):** 27 deliberate bugs in `validate.ts`, `process-store.ts` and `fetcher.ts` (one signal enough, the body marker rule, the password-field and price conditions of the login rule, the shell thresholds, the empty-listing and no-discount conditions, structured data read from scripts, amounts read from visible text, `blocked` ending a sale, `unverifiable` called content-verified, reading every class, the truncated flag not reaching the validator, the validator injection, the error handling, the byte counts and the 3 MiB limit). The Dev's tests caught 23. **Four survived and three are now caught by new tests** (the 100,000 count cap; the `truncated` flag reaching the validator, a cut page being `unreadable` and not `no_discounts`; and a single chunk longer than the read limit being flagged truncated). The fourth, `finalUrl` in the pipeline step, is an equivalent mutant: a redirect to another site or to the home page is already the class `redirected_away`, which is never read, so the validator's own redirect rule cannot fire from the pipeline.
