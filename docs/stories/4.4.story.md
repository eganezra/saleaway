# Story 4.4: CI/CD and Domain

## Status

Approved

## Story

**As the** operator,
**I want** automatic deploys on push and the real domain connected,
**so that** releases are quick and safe, and the site is reachable at saleaway.online.

## Acceptance Criteria

1. Pushing to the main branch builds, tests and deploys to Cloudflare automatically, applying new database migrations first.
2. A failing build or test stops the deploy.
3. The repository secrets (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`) are set, and no secret is in the repository (NFR10).
4. saleaway.online (and www) points to the deployed site over HTTPS. If the domain is not yet on Cloudflare, the steps are documented and launch uses the temporary `workers.dev` address. *(Clarified by the SM on 2026-10-31: the domain **is** on Cloudflare, so the first branch applies; `www` is served by the same Worker and sends visitors to the apex address, see "Decision 3".)*
5. Page caching is confirmed to work on the real domain (a repeated request is served from cache), and the result is noted (see Story 2.4, AC5).
6. Cookie-free Web Analytics is confirmed working on the real domain (see Story 2.5, AC2).
7. A deploy takes less than 5 minutes.
8. The workflow installs the Playwright browser and runs `pnpm test:smoke` (the smoke test with the axe check of Story 2.4) before the deploy step; a failure stops the deploy.

The account ID and the token live only in GitHub's secrets. No account ID or `workers.dev` account address in any tracked file or log excerpt.

Two files, as `unified-project-structure.md` names them. They reuse one set of checks.

- **`.github/workflows/deploy.yml`**: runs on `push` to `main` and on `workflow_dispatch` (so a deploy can be re-run by hand). `concurrency: { group: deploy, cancel-in-progress: false }` (never two deploys at once, never cancel one half way). Jobs: `ci` (`uses: ./.github/workflows/ci.yml`), then `deploy` with `needs: ci` and `if: ${{ github.ref == 'refs/heads/main' && vars.DEPLOY_ENABLED == 'true' }}` (Decision 1: both parts), `runs-on: ubuntu-latest`, **`timeout-minutes: 90`** (the quiet-window wait of Decision 2 can last up to an hour, so a 15-minute job limit would kill it), `permissions: contents: read`. **Every step has its own `timeout-minutes`** so that a hung deploy does not burn the 90: install 10, migrations 5, web deploy 10, the quiet-window wait 65, pipeline deploy 10. Its steps: checkout, pnpm, node, `pnpm install --frozen-lockfile`, then, with `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` from `secrets` set **on the steps that need them only**: (1) `pnpm db:migrate:remote`; (2) `pnpm deploy:web`; (3) `pnpm ci:wait-for-quiet-window` (Decision 2); (4) `pnpm deploy:pipeline`. The order is **migrations, web, wait, pipeline**: additive migrations first so the new code never meets an old table (the architecture says migrations are additive only), the visible site next, the pipeline last and never inside 02:50 to 03:50 UTC.
- **Non-interactive Wrangler:** `wrangler d1 migrations apply` asks "Ok to proceed?" in a terminal. In CI there is no terminal; check in the first real run that it proceeds (set `CI: true`, which Actions sets already) and, if it waits, stop and tell the user; do not pass a flag the Wrangler version does not have.

### Decision 1: the launch deploy must not happen by accident (PO to confirm)

AC1 says a push to main deploys. But the new site has never been live, and the user's standing rule is that the user decides when. So the deploy job is **gated on a repository variable `DEPLOY_ENABLED`** and on the branch being `main`: while the variable is not `true`, a push runs the checks and stops (the job shows as skipped); and a `workflow_dispatch` started on any other branch never deploys (without the `github.ref` check, a manual run on a feature branch would deploy its unreviewed code). The user sets it to `true` as the launch decision (H3) and from then on every push to `main` that passes the checks deploys, as AC1 says. Alternatives: (a) no gate, so the first push to a repository with secrets set launches the site (risk: it launches before the overrides and the morning check); (b) a GitHub "environment" with a required reviewer (not available for private repositories on the Free plan, as far as the SM knows: check before relying on it). **Recommendation: the variable.** It costs nothing and can be flipped back off.

### Decision 2: no pipeline deploy in the nightly window (PO to confirm)

A push at 03:10 UTC would deploy the pipeline in the middle of the nightly run. `pnpm ci:wait-for-quiet-window` runs `scripts/ops/src/wait-for-quiet-window.ts`: if the current UTC time is from **02:50:00 up to (not including) 03:50:00**, it waits until 03:50:00 and exits 0; at any other time it exits at once. The web deploy is not delayed (the web Worker does not take part in the run). `msUntilQuietWindow(now: Date): number` is pure (0 outside the window, the milliseconds to 03:50:00 inside) with tests at 02:49:59, 02:50:00, 03:00, 03:49:59 and 03:50:00. The step is only in `deploy.yml`, before the pipeline deploy. A wait of up to an hour costs Actions minutes; pushes in that window are rare. Alternatives: skip the pipeline deploy in the window (then `main` and the live Worker silently differ until the next push), or fail the run (noisy). **Recommendation: wait.**

### Decision 3: `www` (PO to confirm)

Cloudflare's documentation: a custom domain is exact, with no wildcards ("A Worker on `example.com` won't receive `www.example.com` requests"), one `routes` entry per hostname with `custom_domain: true`, a certificate is issued automatically, and a hostname that already has a `CNAME` cannot be used. The alternative the documentation names for serving both is a redirect rule plus a proxied placeholder DNS record, which are dashboard-only settings and not in the repository. **Recommendation:** attach **both** hostnames to the web Worker (two `routes` entries) and let the Worker answer a `GET` or `HEAD` for `www.saleaway.online` with a **301** to the same path and query on `https://saleaway.online` (the host of `SITE_URL`). It is code, it is tested, and it needs no dashboard rule; every page already declares the apex as its canonical address. `wwwRedirectTarget(requestUrl: string, siteUrl: string | undefined): string | null` in `apps/web/src/lib/host.ts` returns the target or null: only when the request's host is exactly `www.` plus the host of `SITE_URL`, only for `GET` and `HEAD` (the caller checks the method), keeping path and query, never a redirect when `SITE_URL` is missing or invalid (it falls back to the default as `seo.ts` does), and never for the apex or any other host (`wwwxsaleaway.online`, `www.evil.com`, `www.www.saleaway.online`). In `middleware.ts` it runs **before** the page cache, so a redirect is never cached under the wrong key, and the redirect response still gets the site's headers. Tests: the cases above, a query string kept, a path kept, an invalid `SITE_URL`, a `POST` not redirected. [Source: https://developers.cloudflare.com/workers/configuration/routing/custom-domains/]

### The domain (`apps/web/wrangler.jsonc`)

Add `"routes": [{ "pattern": "saleaway.online", "custom_domain": true }, { "pattern": "www.saleaway.online", "custom_domain": true }]`. `SITE_URL` is already `https://saleaway.online`. The first deploy creates the DNS records and certificates; nothing else is configured by hand. Only the web Worker gets a domain: the pipeline stays on its `workers.dev` address (its only public endpoint, `/admin/run`, needs the bearer token). The web Worker's `workers.dev` address stays reachable as well; with indexing off this does no harm, and whether to switch it off at launch is for Story 4.5. The page already carries the beacon when the token is set (manual snippet). The token is public (it is in the page), so it goes in `wrangler.jsonc` and is deployed by CI, like `SITE_URL`. 5. **Not built here:** Dependabot and `pnpm audit` (the deployment architecture suggests them; no acceptance criterion asks), the rate-limit rule and indexing (Story 4.5), the failure alert (Story 4.6), switching off the `workers.dev` address.

### Project Structure Notes

`.github/workflows/ci.yml` and `deploy.yml` are the two files the architecture's tree names. `deploy-window.ts` and `wait-for-quiet-window.ts` sit in `scripts/ops` with the other operator scripts (a CI helper, but the same tools and tests). `host.ts` follows the web app's `lib/` files (`seo.ts`, `headers.ts`). The architecture's sample workflow (one `deploy.yml` with `lts/*`) is replaced by what is built here; Task 10 updates it. No other conflict.

### Testing

- **Framework:** Vitest 5.0.5 (core, ops, web, pipeline) and the Playwright smoke test (unchanged). No test reads the network, a real database or a file outside a temporary folder; the workflow tests read the repository's own two YAML files as text.
- **New tests:** `host.test.ts` (the redirect rules), `deploy-window.test.ts` (the window and its edges), `workflows.test.ts` (the structure rules above).
- **Manual and live checks, recorded in the Dev Agent Record:** the first CI run's time per job; a throwaway pull request with a failing test, to show that a failure stops the deploy (AC2); the deploy's order in the log; `curl -sI` of the home page twice on the real domain (`x-cache`); `www` redirects to the apex; HTTPS on both; the Web Analytics beacon and the dashboard (AC6).
- **All of these must pass from the repository root:** `pnpm lint`, `pnpm typecheck` (with and without `.dev.vars`), `pnpm test`, `pnpm test:smoke`, `pnpm --filter @saleaway/web build`.
