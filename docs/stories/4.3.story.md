### The command (`scripts/ops/src/check-urls-plan.ts`, `check-urls.ts`)

`pnpm ops:check-urls [--dry-run] [--only <slug> ...] [--delay <seconds>]`: **no database and no login** (it needs only the network). It reads `docs/data/retailers-seed.tsv` (through `parseSeedTsv` and `buildSeed`, so "seeded URLs" means exactly what the seed would load) and `docs/data/hidden-stores.json` (through `parseHiddenStores`).

- **`check-urls-plan.ts`** (pure, no I/O, no clock): builds the list of checks (below), turns each answer into a result, builds the report data and its two forms (JSON and Markdown), and decides whether a run is allowed (`canRunNow(previousCheckedAt, now)`: false within 24 hours). Its inputs are plain arrays, so tests pass fixtures.
- **What is checked:** every distinct `https://` **sale address** (92 stores, 85 distinct addresses) and every distinct `https://` **Black Friday address** (68 stores, 64 distinct): **148 pages**, about 84 sites, so about 232 requests with the robots.txt files, about **40 minutes** at 15 seconds a page. A store with no address (the 14 with none) is listed as "no address" and not requested. Stores sharing an address share one request. The 35 hidden stores are marked, because AC6 reports on them separately. Each site's `robots.txt` is requested once and reused for every page of that site.
- **One check** (the same steps as the pipeline, using the shared code of Task 2): `isSafeFetchUrl`, then `checkRobots` (disallowed: `robots_disallow`, no page request; unreachable: `robots_unreachable`), then `fetchPage`, then `classifyResponse` with `redirectedAway` and `knownJsShell` (the store's seed status is `verified_js_shell`; a Black Friday address is never `js_only`). The body is read only for a Black Friday address that answered (`readLimited`, 3 MiB), and then **only its title and first heading are kept in memory** (`firstElementText` for `title` and `h1`), never saved.
- **A page "does not return a successful page" (AC1)** when its class is anything but `ok` or `js_only`: `blocked`, `not_found`, `redirected_away`, `error`, `robots_disallow`, `robots_unreachable`, `unsafe_url`. Those are the flagged URLs. (`js_only` is a pass: the store is known to load products with JavaScript.)
- **The Black Friday year flag (AC5):** from the title and first heading only: `year_2026` if either has 2026; else `year_2025` if either has 2025; else `no_year`; plus whether either says "black friday" (`black_friday_words`). A page that says 2025 and not 2026 is **"stale"**. Nothing is written to the database: all 68 are already unverified and nothing sets the flag to 1; the report lists the stale ones and Story 2.6 uses the flag later. (Footers and scripts say "2025" or "2026" everywhere, so the whole page is deliberately not searched.)
- **The result files** `docs/data/url-check.json` and `docs/data/url-check.md`, written **only after every check finished**: when the run is cut short nothing is written and the command may be run again (stated in its output). The JSON holds `checkedAt`, the user-agent, the delay, and one row per store and kind (`sale` or `black_friday`): slug, kind, class, HTTP status, error word, the Black Friday flags, whether the store is hidden by Story 3.9 and its Worker reason code. **No page text, no address query, no headers.** The Markdown has: the title and the date/time and the computer-side facts; a summary table (how many of each class, for sale pages and for Black Friday pages); **the flagged sale addresses** (store, class, status); **the Black Friday pages that say 2025**; **the 35 hidden stores**, each with its Worker reason and its answer from here, and a count of how many answer (`ok` or `js_only`) from here; and a closing line.
- **`--only <slug>`** (one to three times, each slug must be in the seed file): checks only those stores' sale and Black Friday pages, **prints the results, writes no file and does not start the 24-hour clock**. It exists so the first live contact with real sites is three stores, not 148 pages, and a mistake found there costs nothing. More than three slugs is an error. It still obeys robots.txt, the delay and the user-agent.
- **Once a day:** the command reads the previous `docs/data/url-check.json` and refuses (exit code 1, a plain message saying when it may run again) when its `checkedAt` is less than 24 hours old. There is **no flag to override it**. `--dry-run` makes no request and does not count: it prints how many pages, sites and minutes the real run would take. `--delay` (seconds between pages, default 15, not below 5) exists for tests and slow lines, never to hurry the real run.
- **`args.ts`:** `parseCheckUrlsArgs` (unknown or repeated arguments, `--delay` a whole number of seconds from 5 to 120, `--only` with a bad slug, with a slug that is not in the seed or given more than three times, are errors).
- **Tests** (`check-urls-plan.test.ts`, `args.test.ts`; the command through `runCheckUrls(argv, io)` with a fake `fetch` that records its calls, a fake clock, a fake file system and no real waiting): the list of checks (distinct addresses once, stores with no address skipped, a non-https address skipped and listed, hidden stores marked, a store's Black Friday and sale addresses both checked); the classes (200 `ok`, 200 for a `verified_js_shell` store `js_only`, 403 and 429 `blocked`, 404 `not_found`, a redirect to another site `redirected_away`, a timeout `error`, robots disallow and unreachable, an unsafe address never requested); the year flag on small pages (title only, heading only, both years, footer-only year is ignored, no year); the report (flagged list, the stale list, the hidden table and its count, **no page text, no `http` address and no HTML in the output**, a hostile store name with `|` and `<script>` is escaped); the guard (a previous run 23 hours ago refuses and makes no request, 25 hours ago runs, no previous file runs, a broken previous file is an error and not a pass); every request carries the user-agent; the delay is waited between pages and not before the first; the robots.txt of one site is asked once; an interrupted run writes no file; `--dry-run` makes no request and writes no file; `--only` checks just its stores, writes no file and leaves the guard untouched (a run 1 hour later is still allowed).
- Not built here: any database write by the command, the Black Friday badge (Story 2.6), a standing nightly check, a decision about the hidden stores (Story 5.4).

### Decision 1: where the shared fetcher lives (PO to confirm)

AC6 says the script uses the pipeline's user-agent and rules "as shared code in `packages/core`", and the coding standards say "Shared logic lives in `packages/core`... never copy it into an app". The rules are there (URL safety, robots, classification), but the **polite fetcher and `checkRobots` are in `apps/pipeline`**, and the standards also say "**No I/O in core:** `packages/core` never calls `fetch`, D1 or the clock". The options:

1. **Move them into core and let them take the `fetch` function as an argument (recommended).** They already do: `fetchPage(url, fetchFn)` and `checkRobots(origin, path, fetchFn)` call only the function they are given and read no clock, so they are as testable as the rest of core and the standard's purpose (no hidden network, no clock) is kept. The standard's one line is reworded: "core never calls the global `fetch`, D1 or the clock; code that needs the network takes the fetch function as an argument". No behavior change, tests move with the code. Cost: the pipeline's imports change (a pipeline deploy at the end).
2. Import the pipeline's files from `scripts/ops` by path. Breaks the app boundary, and the pipeline's files import `FetchFn` from the Worker's own types.
3. Copy the fetcher into `scripts/ops`. Two copies of the user-agent and the redirect rules: the standards forbid it, and they would drift.

**Recommendation: option 1.** If the PO prefers a stricter reading of the standard, the alternative is a new small workspace package, which is more structure than this story needs.
