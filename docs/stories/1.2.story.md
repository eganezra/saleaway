## Status

Ready for Review

## Story

**As the** operator,
**I want** the canary site deployed to a free Cloudflare address,
**so that** we find Cloudflare-specific problems early, before the domain exists.

## Acceptance Criteria

1. The web Worker and a pipeline Worker placeholder are deployed with `wrangler deploy`, using the operator's existing Cloudflare login, to `*.workers.dev` addresses. No domain, GitHub repository or CI is needed.
2. The D1 database is created in the Cloudflare account and bound to both Workers, locally and on Cloudflare.
3. `/health` returns OK on the deployed address, and its log line appears in Workers Logs (this also confirms the free logging allowance).
4. The architecture's spike S0 is recorded: whether the Cache API caches responses on `workers.dev`, and the Worker bundle size against the Free plan limit.
5. The README explains the manual deploy and how to roll back (`wrangler rollback`).
6. No secrets are committed (NFR10).

### Adapter bindings

Checked against the Astro Cloudflare adapter docs on 2026-10-29 (outside the architecture docs):

- `imageService` defaults to `'cloudflare-binding'`, which adds the `IMAGES` binding. Setting `imageService: 'passthrough'` (or `'compile'`) avoids it. The architecture stores no images (NFR7, "File Storage: None at launch").
- `session: false` needs Astro 7.2.0 or newer (installed: 7.4.4; confirmed in the installed `astro` config types). It adds no KV binding, provisions no namespace, and leaves the session runtime out of the Worker bundle. The architecture has no KV and no sessions ("Session Management: no sessions").

```js
// apps/web/astro.config.mjs (shape, not final code)
export default defineConfig({
  output: 'server',
  adapter: cloudflare({ imageService: 'passthrough' }),
  session: false,
});
```

[Source: https://docs.astro.build/en/guides/integrations-guide/cloudflare/; architecture/tech-stack.md#technology-stack-table (File Storage and Cache rows); architecture/security-and-performance.md#security-requirements]

### Spike S0 (what to measure and why)

> "S0 (Story 1.2) deploy 'hello' Astro with a D1 binding, and confirm the Cache API works. I believe it does not cache on `*.workers.dev` addresses, so caching may only take effect on the custom domain. This has not been verified, and it also means the home page reads D1 on every view until the domain is connected."

[Source: architecture/risks-and-spikes.md (spike order)]

- Cloudflare's Cache API page says Workers on custom domains have functional cache operations, and says nothing direct about `workers.dev`. Dashboard and Playground cache operations have no effect, and cache entries are per data centre (so repeat requests from one place are the fair test). `put` never caches responses with `Set-Cookie`, and non-GET requests throw. So measure, do not assume. [Source: https://developers.cloudflare.com/workers/runtime-apis/cache/, checked 2026-10-29]
- Why it matters: the home page design relies on edge-cached HTML to protect the D1 daily limits and the 100,000-requests-a-day budget. If `workers.dev` does not cache, the home page reads D1 on every view until Story 4.4 (domain), and the caching is then confirmed in Story 2.4/4.4. State the result, and do not change the design in this story. [Source: architecture/high-level-architecture.md#architectural-patterns; architecture/development-workflow.md#build-order-local-first-decided-2026-10-29]
