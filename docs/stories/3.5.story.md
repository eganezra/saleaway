# Story 3.5: Save Sale Records and Expiry

## Status

Approved

## Story

**As a** bargain hunter,
**I want** the site to show current data and drop ended sales,
**so that** I never get sent to a dead sale.

## Acceptance Criteria

1. Validated results are saved as sale records with percentage, first seen, last checked and last validated (FR9). The record points to the store's sale URL, which is the store's `sale_url` or an active override's, so no URL is copied into the record.
2. A page that fails validation is marked ended (FR10).
3. A temporary failure (blocked, timeout, error) keeps the last good record for up to 72 hours, then the store is hidden, using the visibility rule from Story 2.3 (FR10, NFR3).
4. The home page reads only current records.
5. No retailer product content is stored (NFR7).
6. A `js_only` result (the page answered, products load with JavaScript) saves the record as `active` and `url_verified` and updates `last_validated_at`, so the store stays visible while its page keeps answering (Story 2.3, rule 6).
7. The record's state and validation level come from the verdict of Story 3.3 (`recordEffect`): a valid page is `active` and content-verified, a page with no sale is `ended`, a challenge or login page keeps the last good record, and a page that cannot be judged (a JavaScript page) is `active` and URL-verified. Only `active` results update `last_validated_at`.

- **The verdict rules are in core** (Story 3.3): `ValidationVerdict` is `valid`, `ended`, `blocked` or `unverifiable`, and `recordEffect(verdict)` returns `{ state, validation }`: `valid` is `{ active, content_verified }`, `ended` is `{ ended, null }`, `blocked` is `{ null, null }` (keep the last good record, like a blocked fetch), `unverifiable` is `{ active, url_verified }`. [Source: packages/core/src/validate.ts]
- **The site's rules are in core** (Story 2.3): `resolveStore` hides a store whose record is `ended` (unless an active override sets a percentage), whose freshness time is more than 72 hours old, and so on. The freshness time is the record's `last_validated_at`, or, for a store that has never been validated, `retailers.created_at`. **The home page already reads `sale_records` through that query** (left join), so it needs **no change** here. [Source: architecture/core-workflows.md#state-rules-per-fetch-result]
- **The table:** `sale_records` has `retailer_id` (primary key, references `retailers`), `state` (`active`, `ended`, `unknown`, default `unknown`), `validation` (`content_verified`, `url_verified`, `none`, default `none`), `discount_percent` (null or **5 to 90**, a CHECK; an out-of-range number would make the whole write fail), `last_result`, `first_seen_at`, `last_checked_at`, `last_validated_at`, `ended_at`. There is **no column for the sale URL or any page content**: the URL is `retailers.sale_url` (or an override's). [Source: db/migrations/0001_init.sql; architecture/database-schema.md]
- **Overrides are never touched by the pipeline** (and nothing here writes `overrides`). **`is_visible` and `extraction_method` are never changed by the pipeline.**
- **The live database has 57 visible stores** (35 hidden by Story 3.9): 54 are fetched each night and 3 are `manual` and never fetched. The next run is at 03:00 UTC on 2026-10-31.
- **Time** is UTC `YYYY-MM-DDTHH:MM:SSZ` (`toIsoUtc`). The logger drops fields named `level`, `message` or `time`. SQL only in `repo.ts`. Use `pnpm` and `pnpm exec`, never `npx`. `nvm use` in every terminal.

### The rule (`packages/core/src/sale-record.ts`)

Pure function. It decides what one night's result does to a store's sale record. Types (the fields are the columns of `sale_records` in camel case; `SaleRecordFields` is not the full `SaleRecord` model of the architecture, which has the same fields plus the retailer id):

```typescript
export interface SaleRecordFields {
  state: 'active' | 'ended' | 'unknown';
  validation: 'content_verified' | 'url_verified' | 'none';
  discountPercent: number | null;
  lastResult: FetchClass;
  firstSeenAt: string | null;
  lastCheckedAt: string;
  lastValidatedAt: string | null;
  endedAt: string | null;
}
export interface FetchEvent {
  result: FetchClass;                       // the class of the fetch (Story 3.2)
  verdict: ValidationVerdict | null;        // Story 3.3, or null when the page was not judged
  discountPercent: number | null;           // Story 3.4 will fill this; null until then
  now: string;                              // UTC, YYYY-MM-DDTHH:MM:SSZ
}
export function nextSaleRecord(previous: SaleRecordFields | null, event: FetchEvent): SaleRecordFields | null;
```

`nextSaleRecord` returns the whole new record, or **null for `skipped_manual`** (nothing is written for a manual store). The effect is decided from `event.result` and `event.verdict`, in this order:

1. `skipped_manual`: return null.
2. `js_only`: the effect is `{ active, url_verified }` (AC6).
3. `not_found` or `redirected_away`: the effect is `{ ended }`.
4. `blocked` or `error`: **keep** (see below).
5. `ok` with a verdict: the effect is `recordEffect(verdict)` (AC7). `ok` with **no** verdict (not judged): **keep**.

**Active** (`state` `active`): `validation` from the effect, `discountPercent` from the event **only if it is an integer from 5 to 90**, else null, `lastValidatedAt` = `now`, `endedAt` = null, `firstSeenAt` = the previous `firstSeenAt` when the previous record exists, is not `ended` and has one, else `now` (a new record, or a sale that came back after it ended, is a new sale).
**Ended** (`state` `ended`): `validation` `none`, `discountPercent` null, `lastValidatedAt` unchanged (a failed page is not a validation), `endedAt` = the previous `endedAt` if the record was already `ended` and has one, else `now`, `firstSeenAt` unchanged.
**Keep** (a `blocked` or `error` result, a `blocked` verdict, or an unjudged `ok`): the previous record **unchanged except** `lastResult` and `lastCheckedAt`. If there is no previous record, create `{ state: 'unknown', validation: 'none', discountPercent: null, firstSeenAt: null, lastValidatedAt: null, endedAt: null }` with `lastResult` and `lastCheckedAt` (so the last result is on record; the site judges a never-validated store from `retailers.created_at`).
**In every case** (except `skipped_manual`): `lastResult` = `event.result` and `lastCheckedAt` = `now`.

A temporary failure therefore never ends a sale and never touches `lastValidatedAt`, so the Story 2.3 rule hides the store only after **72 hours without a successful check** (AC3). Nothing here deletes a record. A record has **no URL and no page text** (AC5). [Source: architecture/core-workflows.md#state-rules-per-fetch-result; architecture/data-models.md#salerecord; prd/requirements.md#fr9, #fr10; docs/stories/3.3.story.md (`recordEffect`)]

### The database functions (`apps/pipeline/src/repo.ts`)

- `getSaleRecord(db, retailerId): Promise<SaleRecordFields | null>`: one `SELECT` of the record's columns by `retailer_id`, mapped to camel case (`last_result` is a `FetchClass` or null in an old row: treat null as `error`).
- `saveStoreResult(db, run: RunResultInput, record: SaleRecordFields | null): Promise<void>`: **one `db.batch`** of (a) the same `run_results` upsert as `saveRunResult` and (b) when `record` is not null, `INSERT INTO sale_records (...) VALUES (...) ON CONFLICT(retailer_id) DO UPDATE SET` every column `= excluded.<column>` (the pure function already merged the old values, so the SQL does not use `COALESCE`). A batch is atomic in D1: a result and its record are saved together or not at all. Idempotent: the same job twice leaves one row of each. `saveRunResult` stays for `recordStoreError` and the existing tests. [Source: architecture/backend-architecture.md#data-access-layer (the batch of the record and the result)]

### The pipeline step (`apps/pipeline/src/process-store.ts`)

In `processStore`, replace the single `saveRunResult` by:

1. `const previous = await getSaleRecord(env.DB, job.retailerId)`.
2. `const record = nextSaleRecord(previous, { result: outcome.result, verdict: outcome.validation?.verdict ?? null, discountPercent: null, now: toIsoUtc(finished) })`.
3. `await saveStoreResult(env.DB, { …the same run result as before… }, record)`.

`discountPercent` stays `null` (Story 3.4 reads it). The class, the error text, the status and the duration of the result row do not change. `recordStoreError` (the last-attempt error of a job that threw) does **not** touch `sale_records`. A D1 error in step 1 or 3 throws, as today, so the queue retries the job once and then `recordStoreError` runs. Log nothing new (the `page_validated` line of Story 3.3 is enough). **Free-tier note (coding standards):** one extra read and at most one extra row written per fetched store (54 a night), about 54 reads and 54 writes a day on top of 94 rows written a day: far inside 5,000,000 reads and 100,000 writes. [Source: architecture/backend-architecture.md; architecture/coding-standards.md#critical-fullstack-rules]

### Gaps and decisions for the developer to note

1. **AC1 had said "with ... URL" but `sale_records` has no URL column.** The URL of a sale is `retailers.sale_url` or an active override's `sale_url` (Story 2.3), so nothing is added. **PO ruling 2026-10-30:** criterion 1 now says so (PRD, epic and this story).
2. **An unjudged `ok` page keeps the last record** (the validator failed, the read failed, or `MEASURE_CPU` is on): the SM's decision, the safe side, consistent with "a challenge page keeps the record". It does not refresh `last_validated_at`. **PO confirmed 2026-10-30.**
3. **`unverifiable` refreshes `last_validated_at`** (PO ruling of Story 2.3, criterion 6 and 7): a page that answered but cannot be judged is shown as "On sale" and stays fresh while it answers. A page that is really a dead sale but looks like an unreadable page therefore stays shown; Story 3.6's first real run shows how often.
4. **`first_seen_at`** is set when a record first becomes `active`, and again when a sale comes back after `ended` (a new sale). The SM's reading of "first seen"; the architecture's SQL sample only sets it on insert. **PO confirmed 2026-10-30.**
5. **One bad night ends a sale** (`not_found`, `redirected_away`, or a page with no sale): FR10 says a failing validation is removed "on the next run". The site then hides it at once (Story 2.3). If a store is wrongly `ended`, the operator uses an override until the rule is fixed. **PO confirmed 2026-10-30** (FR10 is explicit); the morning check exists because the rules of Story 3.3 are new, and a false `ended` is the main risk of this story.
8. **The three `manual` stores** (Amazon.co.za, Game, Checkers Sixty60) are never fetched and get no record, so after the web deploy they are hidden 72 hours after they were added (2026-11-01 12:58 UTC) unless an override exists (Story 4.1). Nothing to build here.
6. **Only the nightly and manual runs write records.** A `?store=` run of a hidden store writes its record too, which is harmless: the site only shows visible stores.
7. **`recordStoreError` leaves `sale_records` alone**, so a job that fails twice does not update `last_result`. The result row still shows the error.

### Testing

- **Framework:** Vitest 5.0.5. Core tests are plain unit tests; pipeline tests use the real local D1, the stubbed `fetch` and fake queue messages. No test makes a network request. `pnpm test` must run core, ops, web and pipeline.
- **`packages/core/tests/sale-record.test.ts`** (a fixed `now`, a small builder for `SaleRecordFields`): a table with one test per cell, for **every** class and verdict, with no previous record and with a previous record of each state:
  - `skipped_manual` returns null.
  - `js_only` gives `active` / `url_verified` and sets `lastValidatedAt`.
  - `ok` with each verdict: `valid` is `active` / `content_verified`; `unverifiable` is `active` / `url_verified` (both set `lastValidatedAt`); `ended` is `ended` / `none` (does **not** change `lastValidatedAt`, sets `endedAt`, clears the percentage); `blocked` keeps the record; no verdict keeps the record.
  - `not_found` and `redirected_away` end the sale; `blocked` and `error` keep.
  - **Keep** changes only `lastResult` and `lastCheckedAt`; with no previous record it creates the `unknown` record described above (and `lastValidatedAt` stays null).
  - **First seen:** a new record gets `now`; an active record keeps its first seen across nights; a sale that comes back after `ended` gets a new one; an `unknown` record becomes `active` with `now`.
  - **Ended at:** set once and kept while the record stays `ended`; cleared when it becomes active.
  - **Percentage:** 5 and 90 are kept; 4, 91, 0, 50.5, NaN, a negative number and `null` give null; an ended record has null.
  - **72 hours (with `resolveStore` from Story 2.3):** a record kept for a `blocked` result is still shown 71 hours after its last validation and hidden 73 hours after; a successful night resets it. **AC4:** a record made by `nextSaleRecord` for an `ended` verdict is hidden by `resolveStore` (reason `ended`), and one for a `valid` verdict is shown, so the two pieces fit.
  - `lastResult` and `lastCheckedAt` are set in every non-null case; the input record is never changed; the result holds no page text.
- **`apps/pipeline/tests/repo.test.ts`** (real D1): `getSaleRecord` returns null for no row and the mapped record for a row (and `error` for a null `last_result`); `saveStoreResult` writes the result row and the record together, upserts the same pair twice into one row each, writes only the result when the record is null, and **writes neither when one statement fails** (for example a `discount_percent` of 3, which the CHECK refuses: the result row must not exist either).
- **`apps/pipeline/tests/process-store.test.ts`** (update, do not delete): an `ok` page with a `valid` verdict saves an `active` / `content_verified` record with `last_validated_at` of the run's time and a null percentage; an `ok` page that says no sale (`ended` verdict) saves `ended`, and a **second** night with a valid page makes it `active` again with a new first seen; a `blocked` or `error` result on a store with a record changes only `last_result` and `last_checked_at`, and on a store with none creates an `unknown` record; a `404` ends the sale; a `js_only` store gets `active` / `url_verified`; a `manual` store writes **no** record and no request; a store whose `validate` stub throws (Story 3.3) keeps its record; the `run_results` row is exactly the same as before for every case; **`overrides` and `retailers` are never changed, and no record column holds page text** (read every column of a saved record and check none contains a word of the page). The two old assertions that `sale_records` is empty become "has the expected record".
- **Manual and live checks:** none against retailers. After the deploy, tonight's run writes the first records and the user does the morning check.
- **All of these must pass from the repository root:** `pnpm lint`, `pnpm typecheck` (with and without `.dev.vars`), `pnpm test`, `pnpm --filter @saleaway/web build`.
