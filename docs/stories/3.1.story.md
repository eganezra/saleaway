# Story 3.1: Scheduled Runner with Batching and Run Log

## Status

Done

## Story

**As the** operator,
**I want** a daily job that processes all stores in safe batches,
**so that** it stays within free-tier limits and one failure never stops the rest.

## Acceptance Criteria

1. A Cron Trigger starts the pipeline once every 24 hours (FR4).
2. Stores are split into batches (for example through a queue or several scheduled invocations) sized to stay inside free-tier limits (NFR1).
3. Each run and each store result is written to the run log (FR11).
4. A failure for one store is logged and does not stop other stores (NFR4).
5. Running the job twice does not create duplicate records (idempotent).
6. The job can be triggered manually for testing.
7. A second Cron Trigger closes the run: it records the totals (stores total, ok, failed) and the finish time (FR11).
8. The queue, bindings and the `ADMIN_TOKEN` secret are created and documented, and setting a `PIPELINE_ENABLED` variable to `false` makes the job exit without doing anything (a pause switch).

### Behaviour

**Entry points** (`apps/pipeline/src/index.ts`, `export default { scheduled, queue, fetch } satisfies ExportedHandler<Env, StoreJob>`):

1. **`scheduled(controller, env, ctx)`**: if the pipeline is paused, log `pipeline_paused` (with the cron expression) and return. Otherwise, if `controller.cron === env.FINALIZE_CRON`, run `finalizeRun`; any other cron runs `startRun(env, 'cron')`. The `controller.cron` value is not documented in the Cloudflare docs as an exact string, so **check it** locally (Task 7) and, after the first night, live.
2. **`queue(batch, env)`**: batch size is 1. For each message: validate the body (`{ runId: number, retailerId: number }`; anything else is logged as `bad_job` with the message id and acknowledged, never retried), call `processStore`, and `ack()`. If `processStore` throws unexpectedly: on the first delivery (`message.attempts` below 2) log `process_store_failed` and `retry()`; on the last delivery (`max_retries` is 1, so the second one) **record an `error` result for that store** with the error message (truncated to 200 characters) and `ack()`, so that every store of a run ends with exactly one result and one store never stops the others (NFR4).
3. **`fetch(request, env)`**: `POST /admin/run` with `Authorization: Bearer <ADMIN_TOKEN>`. Any other method or path returns the existing plain `404 Not found` (no hint that `/admin/run` exists). See "The manual run endpoint".

**`startRun(env, trigger, now)`** (`start-run.ts`):

1. Load the ids of the stores to process: `is_visible = 1 AND sale_url LIKE 'https://%'`, ordered by `id` (the same rule as the home page, and the pipeline only ever fetches `https` URLs).
2. Insert a `pipeline_runs` row (`started_at` as `toIsoUtc(now)`, `trigger` `'cron'` or `'manual'`, `stores_total` the number of stores) and read its id.
3. Enqueue one message per store, `{ runId, retailerId }`, with `delaySeconds = position * STAGGER_SECONDS` (position 0, 1, 2, ...), using `sendBatch` in **chunks of at most 100 messages** (the Queues limit). With 92 stores and 15 seconds the last message is delayed about 23 minutes, so the run ends well before the 03:45 close.
4. Log `run_started` (`runId`, `trigger`, `storesTotal`) and return `{ runId, storesTotal }`. If enqueuing fails, log `run_enqueue_failed` and rethrow (the run row stays unfinished and the finalize step will close it with its gap visible).
5. `STAGGER_SECONDS` is parsed as a whole number from 0 to 3600; anything else falls back to 15 with a `stagger_invalid` warning.
6. Zero stores is allowed (a run with `stores_total` 0 and no messages).
7. **No purge of old results here.** The architecture sketch says `start-run.ts` purges results older than 30 days, but retention is Story 4.6 (criterion 3). Do not build it now.

**`processStore(env, job, clock)`** (`process-store.ts`): `clock` is a function that returns the current `Date` (the entry point passes `() => new Date()`), because the step measures its own duration. See "Per-store processing".

**`finalizeRun(env, now)`** (`finalize-run.ts`): find **every** run with no `finished_at` (normally exactly one: today's). For each, count its results by class (`repo.ts`), call `summariseRun`, and update the run: `finished_at`, `stores_ok`, `stores_failed`. Only update rows that are still unfinished (`WHERE finished_at IS NULL`), so running finalize twice changes nothing. A run with fewer results than `stores_total` is still closed; the gap (`stores_total - stores_ok - stores_failed`) is visible in the row, and Story 4.6's alert will treat it as an incomplete run. Log `run_finalized` for each run (`runId`, `storesTotal`, `storesOk`, `storesFailed`, `missing`). No alert yet (Story 4.6).

**Pause switch:** `env.PIPELINE_ENABLED === 'false'` (exact string) means paused; any other value means running. A paused pipeline starts no run (cron or manual) and does not finalize. Messages already in the queue are still processed, and any unfinished run is closed by the first finalize after resuming. Change it with a redeploy or in the Cloudflare dashboard. [Source: architecture/deployment-architecture.md#rollback-pause-and-dependency-upkeep; prd/epic-3-daily-discovery-pipeline.md#story-31 (criterion 8)]

**Result of the "Daily pipeline" workflow in this story:** cron starts, the run row is created, one staggered message per store is enqueued, each message produces a run result, the second cron closes the run with totals. The fetch, classify, validate, extract and `sale_records` steps in the architecture diagram are Stories 3.2 to 3.5. [Source: architecture/core-workflows.md#daily-pipeline; architecture/backend-architecture.md#function-organization, #function-template]

### Per-store processing

`processStore` is a placeholder that **does not fetch anything**. It exists so that the whole fan-out can be built and tested now, and Story 3.2 replaces its body.

- Read the retailer by id (`repo.ts`). If it does not exist, record `error` with `error` = `retailer_not_found`.
- If `extraction_method` is `manual`, record `skipped_manual` (the architecture's rule: manual stores are skipped and their overrides kept). **No fetch is ever made for a manual store**, in this story or later.
- Otherwise record `error` with `error` = `fetcher_not_built_yet`. This is honest (nothing was read), and it will show 89 failures in the first runs. Nothing alerts on it yet.
- Record the result with `saveRunResult`: `run_id`, `retailer_id`, `result`, `http_status` null, `discount_percent` null, `duration_ms` (the time `processStore` took in whole milliseconds, from two calls of the injected `clock`), `error`, and `created_at` from `toIsoUtc(clock())`.
- **No `sale_records` writes** in this story (Story 3.5). Never touch `overrides`.
- Never throw for an expected condition; throw only for real bugs and let the queue handler deal with it as described above.

### Core additions

Add to `packages/core` (pure, tested, exported):

- `toIsoUtc(date: Date): string` returns `YYYY-MM-DDTHH:MM:SSZ` (seconds precision, no milliseconds, UTC). `Date#toISOString()` has milliseconds, so strip them. The coding standards require this format for stored times.
- `summariseRun(counts: Array<{ result: string; n: number }>): { storesOk: number; storesFailed: number }`. **OK results are `ok`, `js_only` and `skipped_manual`.** Everything else counts as failed: `blocked`, `not_found`, `redirected_away`, `error`, **and any value that is not a known class** (so an unexpected value is visible as a failure and not silently dropped). ### Migration 0002

`wrangler d1 migrations apply` runs numbered files in `db/migrations`. Create `db/migrations/0002_run_results_unique.sql`:

```sql
-- db/migrations/0002_run_results_unique.sql
CREATE UNIQUE INDEX idx_run_results_run_retailer ON run_results(run_id, retailer_id);
```

Why: AC 5 (idempotent) and queue redelivery. A message can be delivered twice, and `saveRunResult` is an upsert on `(run_id, retailer_id)`:

```sql
INSERT INTO run_results (run_id, retailer_id, result, http_status, discount_percent, duration_ms, error, created_at)
VALUES (?1, ?2, ?3, ?4, ?5, ?6, ?7, ?8)
ON CONFLICT(run_id, retailer_id) DO UPDATE SET
  result = excluded.result, http_status = excluded.http_status,
  discount_percent = excluded.discount_percent, duration_ms = excluded.duration_ms,
  error = excluded.error, created_at = excluded.created_at
```

The older index `idx_run_results_run` stays (migrations are additive only). The unique index is additive, so rolling code back never needs a database rollback. Running the job twice on the same day creates **two runs**, each with its own results, which is correct (a run is a log entry); it never duplicates a store or, later, a sale record. [Source: architecture/database-schema.md; architecture/database-schema.md#notes; architecture/deployment-architecture.md#rollback-pause-and-dependency-upkeep; architecture/backend-architecture.md#data-access-layer (same `ON CONFLICT` style)]

### The manual run endpoint

`POST /admin/run` is the only public operator endpoint and has **no public admin page**. It uses the `Authorization: Bearer <ADMIN_TOKEN>` header, compared in constant time (the architecture gives `isAuthorized`; put it in `apps/pipeline/src/auth.ts` and unit test it):

```typescript
export function isAuthorized(req: Request, token: string | undefined): boolean {
  const header = req.headers.get('Authorization') ?? '';
  const supplied = header.startsWith('Bearer ') ? header.slice(7) : '';
  if (!token || supplied.length !== token.length) return false;
  let diff = 0;                                  // constant-time comparison
  for (let i = 0; i < token.length; i++) diff |= token.charCodeAt(i) ^ supplied.charCodeAt(i);
  return diff === 0;
}
```

| Case | Response |
|---|---|
| not `POST /admin/run` | `404`, body `Not found` (unchanged) |
| missing, wrong or empty token, or no `ADMIN_TOKEN` configured | `401`, error JSON `code: "unauthorized"` |
| paused (`PIPELINE_ENABLED` is `false`) | `409`, error JSON `code: "paused"` (checked **after** the token) |
| a run was started | `200`, `{ "ok": true, "runId": <number>, "storesTotal": <number> }` |
| unexpected failure while starting | `500`, error JSON `code: "run_failed"` (and a `run_failed` log with the error under `err`) |

Error JSON is the architecture's shape: `{ "error": { "code": string, "message": string, "requestId": string, "timestamp": string } }`, with `requestId` from `crypto.randomUUID()` and `timestamp` from `toIsoUtc`. A manual run **starts a new run and fetches every store again** once the fetcher exists (Story 3.2), which breaks the "one page fetch per store per day" rule if used carelessly (NFR6), so the README says to use it sparingly. There is no `ops:run` script in this story; the README documents a `curl` command that reads the token from an environment variable (decision 6). [Source: architecture/backend-architecture.md#function-template, #authentication-and-authorization, #middlewareguards; architecture/api-specification.md; architecture/error-handling-strategy.md#error-response-format; prd/requirements.md#nfr6]

### Gaps and decisions for the developer to note

1. **The architecture's test tool cannot be used.** `@cloudflare/vitest-pool-workers` needs Vitest 4 and the repository is on Vitest 5. This story uses `getPlatformProxy` with a real local D1 (verified by the SM). The architecture and tech-stack docs are updated to say so.
2. **A new migration is needed for idempotence.** `run_results` had no uniqueness on `(run_id, retailer_id)`. Migration 0002 adds a unique index and `saveRunResult` is an upsert, so a redelivered message cannot create a duplicate result. **PO ruling (Sarah, 2026-10-29) on how to read criterion 5:** "safe to repeat" means that repeating a run, or redelivering a message, never creates a duplicate **store, sale record or result for the same run and store**. Each run is itself a legitimate log entry, so two runs in one day produce two sets of results. That reading is what Story 3.1 builds and tests; Story 3.5 applies the same rule to `sale_records` with an upsert on `retailer_id`.
3. **What counts as "failed" is defined here.** `pipeline_runs` only has `stores_ok` and `stores_failed`, and no document says which result classes belong to which. OK is `ok`, `js_only` and `skipped_manual`; failed is everything else, including unknown values. Stories 4.2 (health report) and 4.6 (alert above 20 percent failed) use these totals. If the PO wants `not_found` or `redirected_away` counted differently, change `summariseRun` in one place.
4. **The per-store step is a placeholder** and records `error` / `fetcher_not_built_yet` for 89 stores, and `skipped_manual` for the 3 manual stores. Nothing reads these results yet, and nothing alerts. Story 3.2 replaces it.
5. **Finalize closes every unfinished run**, not only the newest, and closes a run even if some results are missing (the gap shows in the totals). A pause stops new runs and finalizing but not messages already queued.
6. **No `ops:run` script.** The architecture lists `pnpm ops:run` in the operator CLI but no story builds it. The README documents the `curl` call instead, so no script has to handle the token. It can be added with Story 4.2.
7. **Manual runs break the politeness rule once fetching exists** (a second fetch of every store in a day, NFR6). Today a manual run fetches nothing. Story 3.2 should decide whether a manual run may target one store.
8. **`controller.cron` is compared with `FINALIZE_CRON`**, as in the architecture sketch. If the string ever differs (a typo, or Cloudflare formats it differently), the 03:45 trigger would start a second run instead of closing the first. The local check and the next-morning live check exist to catch this. A safer design (an explicit `START_CRON` variable and an error for an unknown cron) is a candidate follow-up.
9. **The live cron and finalize path are only proven the morning after** (see "Live checks"). The code paths are covered by tests with a real D1 and by the local `--test-scheduled` run.
10. **Queue consumer CPU:** the Queues docs say 30 seconds by default for both plans, the architecture assumed 10 ms. Do not rely on either; Story 3.2 measures it.
