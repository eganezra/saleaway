# Story 1.4: First Live Store List

## Status

Ready for Review

## Story

**As a** bargain hunter,
**I want** to see a list of stores with sales and click through to them,
**so that** I can start finding deals right away.

## Acceptance Criteria

1. The home page reads visible stores from D1 and shows one card per store with the store name and "On sale".
2. Each card links to the store's sale URL in a new tab, with `rel="noopener"`.
3. The page works on a phone-width screen.
4. The page works locally and on the deployed `workers.dev` address.
5. Page reads handle an empty or failing database gracefully, with a friendly message.

### What the page is, and is not

- **Is:** a plain, readable list. One link card per visible store showing the store's name and "On sale", in the order the data comes back (category order, then store rank). A short heading and one intro line above it.
- **Is not:** grouped by category (2.2), a discount percentage or "checked" time (2.1, Epic 3), filtered by sale age or overrides (2.3), cached (2.4), SEO-tagged (2.4), or counted by analytics (2.5). The query does **not** read `sale_records` or `overrides`.
- "Visible" in this story means `is_visible = 1` **and** the store has an `https://` sale URL. [Source: prd/epic-1-foundation-first-live-page.md#story-14; prd/epic-2-public-site.md#story-23]

### The query

One query, one round trip (the architecture's "one query for visible sales"). It was run against the live database by the SM: 92 rows, `rows_read` 290, about 10 KB of JSON.

```sql
SELECT r.slug, r.name, r.sale_url
FROM retailers r
JOIN categories c ON c.id = r.category_id
WHERE r.is_visible = 1 AND r.sale_url LIKE 'https://%'
ORDER BY c.sort_order, r.rank, r.id
```

- Expected result today: **92 rows**. First five: Takealot, Temu (SA storefront), Bash (TFG), Makro, Bob Shop. Last three: Canine & Co, Family Pet Centre, Benji + Moon. Rows per category, in order: 11, 10, 13, 10, 10, 6, 9, 10, 5, 8.
- `getVisibleStores` maps `sale_url` to `saleUrl` and **also** drops any row whose URL does not start with `https://` (defence in depth: an operator can set a URL by hand, and a `javascript:` link must never reach an `href`).
- Data access goes through `lib/db.ts` only. No SQL anywhere else in the web app. [Source: architecture/core-workflows.md#page-view; architecture/frontend-architecture.md#component-organization; architecture/coding-standards.md#critical-fullstack-rules; architecture/database-schema.md]


### Page states

| State | When | Response | What the visitor sees |
|---|---|---|---|
| `ok` | the query returns 1 or more stores | 200 | heading, intro line, the list of cards |
| `empty` | the query works and returns 0 rows | 200 | the friendly message |
| `error` | the query throws (database unavailable, missing table, anything) | **503** | the same friendly message |

- Friendly message, exactly: **"Sales are loading, check back soon."** Short, no technical detail, no error text, no SQL, no stack. It is a full-width card in the standard card style (the spec's "Empty / Error Message", variants "no data" and "loading failed").
- The architecture says a failing database returns 503 (and later, once caching exists, serves a cached copy first). The architecture gives no status for an empty but healthy database, so this story uses 200 for it (decision 2 below).
- Set the status in the page with `Astro.response.status = 503`.
- `loadHomeViewModel` logs only the failure: `log.error('home_failed', { err })`. **Do not log on a successful view**: the Free Workers Logs allowance is 200,000 events a day and every page view would use one.
- When no cached copy exists the friendly card is shown. Serving a cached copy on failure is Story 2.4.

[Source: architecture/error-handling-strategy.md#frontend-error-handling; front-end-spec.md#empty--error-message; front-end-spec.md (information architecture: "No data or database error: show a friendly full-width message")]

### Store card

One card per store, and the whole card is **one link** (spec: "the row is one link").

```html
<li>
  <a href="https://…/sale" target="_blank" rel="noopener noreferrer" data-store="takealot">
    <span class="name">Takealot</span>
    <span class="label">On sale</span>
    <span class="visually-hidden">(opens in a new tab)</span>
  </a>
</li>
```

- The cards sit in a real list (`<ol>`; no visible numbers), inside one `<main>`.
- `target="_blank"` with `rel="noopener noreferrer"`. The epic asks for `rel="noopener"`; the Security section specifies `noopener noreferrer`, which includes `noopener`, so it satisfies both. (`noreferrer` also hides the referrer from the store.)
- `data-store="<slug>"` is included now because the Story 2.4 smoke test selects `a[data-store]` and Story 2.5's click beacon reads it. Nothing uses it in this story.
- The accessible name reads, for example, "Takealot On sale (opens in a new tab)". The extra words are a visually hidden span, not an ARIA attribute.
- The store name **wraps** to a second line and is never cut off with an ellipsis. The longest name today is `Petshop Science (on Checkers Sixty60)`. Escape every value (Astro does this by default). No database value is rendered as raw HTML.
- Text only. No retailer images, logos or favicons (NFR7).

[Source: front-end-spec.md#store-row; architecture/security-and-performance.md#security-requirements (outbound links, XSS prevention); architecture/frontend-architecture.md#component-template; architecture/testing-strategy.md#e2e-test (`a[data-store]`); prd/requirements.md#nfr7]

### Gaps and decisions for the developer to note

1. **The page data returns a result instead of throwing.** The architecture sketches `try { vm = await loadHomeViewModel(db) } catch { renderEmptyState(503) }` in the page. This story keeps the same behaviour but moves the `try/catch` into `loadHomeViewModel`, which returns `ok`, `empty` or `error`, so the failure and empty branches can be unit tested (page code in `.astro` files is not unit tested).
2. **Empty database gives 200, a failing database gives 503.** The architecture specifies 503 only for an unavailable database. A healthy database with no visible stores is not a server error. Both show the same message.
3. **`rel="noopener noreferrer"`** instead of the epic's `rel="noopener"` (see "Store card"). It satisfies the criterion.
4. **Ordering.** The architecture says rows within a category are ordered by biggest discount, then rank (FR14, Story 2.2). No discounts exist yet, so this story orders by category then rank only, with no category headings. That keeps Story 2.2's grouping a small change.
5. **"On sale" is unverified.** Until the pipeline exists (Epic 3), the page claims "On sale" for every visible store, and 19 of the 92 sale URLs have never been fetched (status `search_only`; Story 4.3 checks them). Another 19 are JavaScript-only pages that can only ever be URL-verified. The `workers.dev` address is not listed or linked anywhere. Do not promote it, and do not point a domain at it, until Epics 2 and 3 are done.
6. **No caching yet**, so every view reads D1 (see "Free-tier impact"). Caching is Story 2.4.
7. **Interim copy.** The heading and the intro line are placeholders for Epic 2's hero.
8. **Static asset requests.** The two stylesheets are served as static assets by the Worker's `ASSETS` binding. Whether those requests count toward the 100,000 requests a day is still unverified in the architecture ("Verify at scaffold time"). If you notice evidence either way (for example in the dashboard request count), record it in the Dev Agent Record. Do not spend time measuring it.
