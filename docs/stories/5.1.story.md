# Story 5.1: JavaScript-Only Store Support

## Status

Approved

## Story

**As a** bargain hunter,
**I want** discounts shown for stores that load products with JavaScript,
**so that** big stores such as Takealot show a real percentage.

## Acceptance Criteria

1. For stores flagged as JavaScript-only, the pipeline either uses a browser render within free-tier limits or a store's data endpoint to read prices.
2. The method is chosen per store through `extraction_method`. *(Clarified by the SM on 2026-11-01: the column `extraction_method` has a database CHECK that lists its four values, and SQLite cannot change a CHECK without rebuilding the table, which the project's additive-migrations rule forbids; so the choice per store is a new additive column `fetch_mode`, see "Decision 1".)*
3. The number of stores moving from "On sale" to a percentage is reported.
4. The approach stays within NFR1 and NFR6.

[Source: prd/epic-5-coverage-growth-post-launch-before-black-friday.md#story-51-javascript-only-store-support]

### The rules for this story

- **Politeness first (NFR6).** A browser render may happen **at most once per store per day** (the nightly run, plus a user's test run), only after the store's `robots.txt` allows the page (`checkRobots`, as today), with the user-agent **set to the bot's** (`USER_AGENT`) and **no attempt to hide the browser or to get past a store's protection** (no stealth plugin, no changed fingerprint, no solving of a challenge). A store that blocks the render is **left as it is** ("On sale") and recorded; nothing is done to get round it.
- **Keep the footprint small.** A browser page load makes several requests to the store (its scripts and data calls). So: the page is loaded **once**, **images, fonts, media and style sheets are not downloaded** (request interception), nothing is clicked or scrolled, no other page of the store is visited, and the browser is **always closed** (also on an error).
- **No retailer request except the user's three spike runs and the nightly run.** No `curl`, no local headless browser against a store, no extra manual run. The Dev **never sees the `ADMIN_TOKEN`**: the user triggers the test runs (Task 4).
- **The free daily budget is shared by everything** (the nightly run, the user's test runs, any manual run): plan for **at most 8 of the 10 minutes**, see "The budget". Do not run the tests between 02:50 and 03:50 UTC (the nightly run uses the budget then).
- **No other dependency, no change to the web app, no change to a verdict rule or an extractor.** The only new package is `@cloudflare/puppeteer`. Nothing is deployed by hand: the push deploys. If anything needs a paid plan, **stop and tell the user first** (NFR1). [Source: docs/prd/requirements.md; architecture/coding-standards.md]

### The design

- **Decision 1: the choice per store is a new column.** `db/migrations/0004_fetch_mode.sql`: `ALTER TABLE retailers ADD COLUMN fetch_mode TEXT NOT NULL DEFAULT 'plain' CHECK (fetch_mode IN ('plain','browser'));` (additive; every store stays `plain`). `extraction_method` keeps meaning how to read the page's content (`html`, `structured_data`, `shopify_json`, `manual`); `fetch_mode` says how the page is obtained: a plain fetch, or a browser render. The seed never changes it (like `extraction_method`); an operator switches a store with a one-row `UPDATE`, read back (README: how). `fetch_mode` is added to `RetailerForJob` (`repo.ts` selects it) and to `getVisibleRetailerIds` (which today returns ids only) so that `start-run.ts` can plan the lanes.
- **The render lane (`start-run.ts`).** Plain stores keep `index x 15` seconds (the index among the plain stores only). The stores with `fetch_mode = 'browser'` get their **own lane**, `n x 25` seconds for the n-th such store (the free plan allows a new browser every 20 seconds; 25 keeps a margin), starting at 0. The two lanes run side by side (consumer concurrency is 2, the plan allows 3 browsers). A pure function `lanesDelays(stores, staggerSeconds, renderGapSeconds)` returns the delay of every store; the message delay cap of the queue is not reached (21 stores x 25 s is under 9 minutes).
- **The budget guard (`render.ts`, pure part `renderAllowed`).** Before a render, read the browser time already used **today (UTC)**: `SELECT COALESCE(SUM(rr.duration_ms), 0) FROM run_results rr JOIN retailers r ON r.id = rr.retailer_id WHERE r.fetch_mode = 'browser' AND rr.created_at >= ?` (today at 00:00:00Z). The total of a store's time is more than its browser time, so this over-counts, which is the safe side. If `used + RENDER_MAX_MS` would pass the budget (`BROWSER_BUDGET_SECONDS`, a `wrangler.jsonc` variable, default `480`), **do not render**: the store is saved as it is today (`js_only`, error word `browser_budget`) and a `render_skipped` line is logged. `RENDER_MAX_MS` is 30,000 (the most one render may take: navigation timeout 20 s, then a short wait for the product list, then close).
- **The renderer (`render.ts`).** An interface `Renderer` with one method, `render(url): Promise<RenderResult>` (`{ status, finalUrl, html, ms }`), injected through `Deps` (`deps.render`), so tests pass a fake and **no test starts a browser**. The real one uses `@cloudflare/puppeteer` with the `BROWSER` binding: launch, one page, `setUserAgent(USER_AGENT)`, request interception that aborts `image`, `font`, `media` and `stylesheet` requests, `goto(url, { waitUntil: 'domcontentloaded', timeout: 20000 })` and then a bounded wait of **at most 8 seconds for the rendered text to contain a price** (`page.waitForFunction` on `document.body.innerText` matching `R` followed by digits, the same shape as the validator's `PRICE`); when the 8 seconds pass with no price, the page is taken as it is (the validator then judges it), `content()` limited to 3 MiB (the same `MAX_PAGE_BYTES`), and `close()` in a `finally`. It never throws: a failure is `{ ok: false, reason }` with a short word (`timeout`, `launch_failed`, `rate_limited`, `navigation_failed`...). Its rate-limit answer when a browser cannot be started is `rate_limited`, treated like any failure (the store keeps "On sale"; **no retry in the same run**).
- **The browser branch (`process-store.ts`, `fetchAndClassify`).** For `fetch_mode = 'browser'`: robots first (unchanged); then the budget guard; then `render`; the HTTP status and final address go through `classifyResponse` and `redirectedAway` exactly as a plain fetch does (`blocked`, `not_found`, `redirected_away`, `error`; `knownJsShell` is **false** for a render store, so a 2xx is `ok`, not `js_only`); the rendered `html` then goes to `validateSalePage` and `readPercent` unchanged, and the result is saved as any other. Any render failure leaves the store `js_only` with the reason word. **A render store must never render twice for the same run.** Queue delivery is at least once and a message can be retried or delivered again, and `saveStoreResult` is an upsert (`ON CONFLICT ... DO UPDATE`): it **overwrites** a second result, it does not refuse it. So, before any render, read whether `run_results` already holds a row for this run and store (`SELECT 1 FROM run_results WHERE run_id = ? AND retailer_id = ?`, one query; the per-invocation budget of 50 D1 queries is far away); if it does, **do not render and do not overwrite**: return. A render failure is a result and not an exception, so it is not retried.
- **Logging.** One `page_rendered` line per render: slug, status, bytes, `ms`, whether truncated; one `render_skipped` line when the budget stops it. Numbers and short words only, never page text.
- **`Env` and config.** `BROWSER: Fetcher` and `BROWSER_BUDGET_SECONDS` in `apps/pipeline/src/env.d.ts` / the generated types; `"browser": { "binding": "BROWSER" }` and `"BROWSER_BUDGET_SECONDS": "480"` in `apps/pipeline/wrangler.jsonc`. The free-tier note: the render adds no D1 write (one `SELECT` for the budget per render store) and no Worker request.

### The budget

10 minutes a day is 600 seconds; the guard stops at 480. If an average render takes 15 seconds, 21 stores use about 315 seconds a day, which fits; if it takes 25 seconds, only about 19 fit and the user's own test runs share the same day. **The Dev records the real browser time per store** (the `page_rendered` lines) and switches stores on only while `(stores switched on) x (the average time) + a day of test runs` stays below 480 seconds, and says plainly how many that is. If even the three of the spike do not fit, that is the finding.

### The spike (the gate, Task 4 and 5)

Three stores through the real thing before anything is enabled: `takealot`, `woolworths-all-depts`, `superbalist`. The Dev ships the dormant code and sets `fetch_mode = 'browser'` on those three (one-row updates, read back). The **user** then triggers a **manual run for one store at a time**, with their `ADMIN_TOKEN` (the README's "Run it by hand": `POST /admin/run?store=<slug>`), **at least a minute apart and never between 02:50 and 03:50 UTC**, and tells the Dev the run's number; the Dev reads the result with `pnpm ops:coverage --remote --run <id>` and the Workers Logs the user exports if the lines are needed (as in Story 3.6). **The gate:** the spike passes for a store when a render returns status 200 with a page that `validateSalePage` judges `valid` and that gives a percentage, within `RENDER_MAX_MS`, **without** the store's protection stopping it, **and** with the user-agent confirmed (during the spike only, the render logs `navigator.userAgent` as the page itself sees it, which must be the bot's `USER_AGENT`). If a store passes, the spike is a success for that store. **If none of the three passes, HALT**: report why (blocked, nothing readable even rendered, over time, or the free plan's limits) and the options for the PO (Decision 2).

### Decision 2: what if the browser does not work (PO to confirm)

Plausible outcomes of the spike and the recommended response:
1. **Some stores work, some do not.** Switch on the ones that work; the others stay "On sale". (Expected.)
2. **Browser requests are blocked** (the stores that bot-protect against Cloudflare's own network will likely do so: Cloudflare says Browser Run is "always identified as bot traffic"). Nothing is done to get round it (NFR6); the stores stay "On sale". The remaining option for a big store is **a manual override** with a percentage (Story 4.1) or, for a store whose public data feed has a standard shape, the existing `structured_data` or `shopify_json` extractors; a store-specific data endpoint needs its own parser and is **out of this story** (it would be a story of its own, per store).
3. **The free allowance is too small.** The Workers Paid plan removes the browser-time limit (it is charged by use); that is a paid plan and **must be put to the user first (NFR1)**. The SM has not checked its price.

**Recommendation:** run the spike; do not decide anything about a paid plan before it shows what the stores allow.

### Decision 3: what AC1's "data endpoint" means here (PO to confirm)

AC1 allows "a browser render **or** a store's data endpoint". This story does the browser render. A store's data endpoint is a different JSON shape for every store, so it is one small parser per store, with its own `robots.txt` question, and the SM judged it a separate story if the spike leaves big stores unread. Stores that already expose a standard shape (Shopify's product feed, JSON-LD) are handled by the existing extractors.

### Decision 4: how NFR6's "one page fetch per store per day" is read (PO to confirm)

A browser loads a page and the page's own scripts and data calls: several requests, not one. The SM reads NFR6 as **one page load per store per day**, with images, fonts, media and style sheets switched off, no other page visited, `robots.txt` obeyed and the bot's own user-agent. If the PO reads it as one request, a browser cannot meet it and the story reduces to the data-endpoint option.

### Testing

- **Framework:** Vitest 5.0.5. **No test starts a browser or touches the network**: the renderer is injected (`deps.render`), and the puppeteer adapter is tested against a fake `puppeteer` object (its `launch`, `newPage`, `setUserAgent`, `setRequestInterception` and `on('request')`, `goto`, `content`, `close`).
- **`render.test.ts`:** `renderAllowed` (under the budget; exactly at it; over; zero used; a negative or missing sum is an error and not a pass); `lanesDelays` (plain stores 0, 15, 30...; render stores 0, 25, 50...; mixed order; no render stores; one store; the two lanes are independent); the adapter: the user-agent is set to `USER_AGENT` before `goto`, image, font, media and style sheet requests are aborted and a script and an XHR are allowed, the browser is closed after success, after a navigation timeout and after a thrown error, the content is cut at 3 MiB, a launch failure and a rate-limit answer give `launch_failed` and `rate_limited`, nothing is thrown, and exactly one page is opened and one `goto` is made.
- **`process-store.test.ts` (new cases):** a `plain` store never calls the renderer; a `browser` store renders, is validated and gets its percentage from the rendered page (a small page sample with a discount); the render's status 404 and 403 become `not_found` and `blocked`; a render to another site is `redirected_away`; a failed render saves `js_only` with its reason word and does not throw; a message for a store that already has a result in this run (a redelivery) means **no second render and no overwrite**; a robots refusal means **no render**; an exhausted budget means no render and `js_only` with `browser_budget`; `knownJsShell` is not applied to a render store; a `manual` store is still never rendered; the `page_rendered` line holds no page text.
- **`start-run.test.ts` / `repo.test.ts`:** the lane delays are used for the messages; `fetch_mode` is read and defaults to `plain`; the migration applies to a database that already has data and leaves every store `plain`.
- **Manual checks, recorded in the Dev Agent Record:** the bundle size; the three spike results; the browser time per store; each switch read back; the before and after counts.
- **All of these must pass from the repository root:** `pnpm lint`, `pnpm typecheck` (with and without `.dev.vars`), `pnpm test`, `pnpm test:smoke`, `pnpm --filter @saleaway/web build`.
