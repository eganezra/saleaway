# Story 4.1: Manual Override Command

## Status

Approved

## Story

**As the** operator,
**I want** to override a store's discount, visibility or URL,
**so that** blocked or broken stores still look right.

## Acceptance Criteria

1. A documented command or script can set a manual discount percentage, hide or show a store, and change its sale URL (FR12). Hiding a store here (an override) is not the same as hiding it with `is_visible` (Story 3.9): an override hide only removes the store from the site, and the pipeline still fetches it.
2. An override can have an expiry date, after which it stops applying.
3. Overrides win over extracted values, and the pipeline never deletes them.
4. Changes take effect on the site without a redeploy, within the page cache lifetime of about 10 minutes (FR3). The override precedence rules themselves are built in Story 2.3.
5. Amazon.co.za, Game and Checkers are set to manual by default.
6. `ops:override --export` saves all overrides to a file in the repository, so the hand-entered data can be restored.
7. Values passed to the command are validated before they are used in SQL (see Coding Standards in `docs/architecture.md`).
8. A store hidden by Story 3.9 can be shown with manual values in one step: the command sets it to the `manual` method (so the pipeline never fetches it again), makes it visible, adds the manual override, and removes the store from `docs/data/hidden-stores.json`. Without the `manual` method, showing it would make the pipeline fetch a blocked store every night.

### The freshness change (Task 2; confirmed by the PO on 2026-10-30)

Story 2.3 made an active override count as "a fresh check" **by its creation time**: the store is shown for 72 hours after the override was made, and then it is stale again. For a `manual` store (never fetched, no record) that means an override is **worthless after 3 days**, and an `--expires` date more than 3 days away has no effect. The SM's reading of FR10 ("an active override counts as a fresh check") and of the command's purpose is that **an override keeps the store fresh for as long as it is active** (until `expires_at`, or for ever if it has none). The change, in `resolveStore`:

- rule 6 (stale) no longer judges a store that has an **active** override: it is not stale. `freshAt` in the view is `now` for such a store. The other rules are unchanged (the flag, the https URL, the override hide, `ended`).
- A store **without** an active override is judged exactly as before (the record's `last_validated_at`, or `retailers.created_at` for a store never validated).
- Update `packages/core/tests/visibility.test.ts`: the tests named "counts an active override as a fresh check, whether it sets a percentage or only a URL" (it asserts `freshAt` is the override's `createdAt`), "does not count an expired override as a fresh check" (still true) and "keeps a stale store hidden when the override is older than 72 hours too" (now the store is shown), plus one new test: an active override created 10 days ago keeps a never-validated store shown; the same override once expired does not; an override with no expiry keeps it shown. In `apps/web/tests/home-view-model.test.ts` check the test about an old override; it should still pass.
- Update the sentence about the freshness time in `core-workflows.md` (shard and `docs/architecture.md`, identical) and the README paragraph "Which stores the page shows": "an active override counts as a check" becomes "while an override is active the store is not judged stale".

The web app is not deployed, so this changes nothing on the live site. [Source: docs/stories/2.3.story.md (rule 6); prd/requirements.md#fr10, #fr12; architecture/core-workflows.md#state-rules-per-fetch-result]

### The rules (`packages/core/src/override-input.ts`)

Pure functions, so that the command and, later, an admin page validate in one place. [Source: architecture/coding-standards.md#critical-fullstack-rules (shared logic in core, no I/O)]

```typescript
export interface OverrideChange {            // what the operator asked for; `undefined` means "leave as it is"
  percent?: number | null;                   // an integer 1 to 99, or null to clear
  hide?: boolean;
  saleUrl?: string | null;                   // an https URL accepted by isSafeFetchUrl, or null to clear
  expiresAt?: string | null;                 // YYYY-MM-DDT23:59:59Z, or null to clear
  note?: string;                             // at most 200 characters, no control characters
}
export type ChangeResult = { ok: true; change: OverrideChange } | { ok: false; errors: string[] };
export function parseOverrideChange(raw: { percent?: string; hide?: boolean; saleUrl?: string; expires?: string; note?: string }, today: string): ChangeResult;
export function expiryFromDate(date: string): string;   // '2026-11-30' -> '2026-11-30T23:59:59Z'

export interface OverrideRow { slug: string; discountPercent: number | null; hide: boolean; saleUrl: string | null; expiresAt: string | null; note: string; createdAt: string }
export function parseOverridesFile(value: unknown): OverrideRow[];   // throws one Error naming every problem
```

- `parseOverrideChange` takes the raw text of each option and returns the typed change **or every error at once** (not only the first): `percent` is the text `none` (clear) or a whole number from **1 to 99** (the table's CHECK; this is wider than the 5 to 90 of an extracted percentage); `saleUrl` is `none` or an address for which `isSafeFetchUrl` is true; `expires` is `none` or a real calendar date `YYYY-MM-DD` that is **today or later** (`today` is `YYYY-MM-DD`, passed in; a date in the past is refused because it would never be active), converted by `expiryFromDate`; `note` is at most 200 characters with no control characters (a quote is allowed: the SQL builder doubles it). It also refuses a change that sets nothing (no field given).
- **`expiryFromDate`** gives the **end of that day in UTC**, so an override "until 2026-11-30" applies through that whole day. (South Africa is two hours ahead of UTC, so it ends at 01:59 the next morning local time.) **[SM decision: the PRD says "an expiry date"; the architecture's example is `--expires 2026-11-30`.]**
- **`parseOverridesFile`** validates the export file: an array of rows, each with a slug that matches `^[a-z0-9-]+$`, an integer percent from 1 to 99 or null, a boolean `hide`, a `saleUrl` that is null or `isSafeFetchUrl`, an `expiresAt` that is null or `YYYY-MM-DDTHH:MM:SSZ` and a real date-time, a `note` of at most 200 characters without control characters, a `createdAt` that is `YYYY-MM-DDTHH:MM:SSZ`, **no duplicate slug**, and at most 500 rows. One `Error` naming every problem (the style of `parseHiddenStores`).

### The command (`pnpm ops:override`)

`scripts/ops/src/override.ts`, built like `hide.ts` (see "Previous Story Insights"). Exactly one of `--local` or `--remote` is required, and exactly one **mode**:

| Mode | Arguments | What it does |
|---|---|---|
| change (the default) | `--slug <slug>` and at least one of `--percent <1-99 or none>`, `--hide`, `--unhide`, `--url <https url or none>`, `--expires <YYYY-MM-DD or none>`, `--note <text>`, or `--bring-back` | creates or changes this store's override |
| `--clear` | `--slug <slug>` | deletes this store's override |
| `--list` | none | prints every override (read-only), with whether each is active or expired |
| `--export` | none | writes every override from the database to `docs/data/overrides.json` |
| `--import` | none | restores the overrides from `docs/data/overrides.json` into the database |

- **Change:** the override is **created** if the store has none, otherwise **only the fields named are changed**: a field that is not mentioned keeps its value (`none` clears `--percent`, `--url` and `--expires`; `--hide` sets the hide flag and `--unhide` clears it; `--note` replaces the note). `created_at` is **set to now on every change** (it is the time the operator last looked at the store). One `INSERT ... ON CONFLICT(retailer_id) DO UPDATE SET` whose `SET` lists only the fields named, plus `created_at`. The slug must be the slug of an **existing** store: the command first reads `id` for the slug (and the store's `sale_url`, `extraction_method` and `is_visible`) and stops with a clear message if there is none; the SQL then uses the numeric id (validated with `sqlInt`), never the text.
- **`--bring-back`** (AC8) also changes the **store**: `extraction_method` becomes `manual` and `is_visible` becomes 1, in the **same SQL file** as the override (see the order below). It also **clears the hide flag** (bringing a store back means showing it; `--bring-back` with `--hide` is refused). The override is written **first and the store `UPDATE` second**, in the same SQL file, so a run that stops half way never leaves a store visible without its override (Wrangler does not promise that a file runs as one transaction, so the read-back below checks both). It refuses when the store would have **no https sale address** (its own `sale_url` is not `https://...` and no `--url` is given), because a manual store is shown by its address. The override row is created or changed as above (at least `created_at` is set, so the store is fresh). **On `--remote` only**, after the database check passes, the store's entry is **removed from `docs/data/hidden-stores.json`** (if it is there) and the file is rewritten in the same format (the key order and two-space indentation it has now, a final newline) and re-read with `parseHiddenStores` to check it is still valid; on `--local` the file is **never touched**. A warning is logged when no `--expires` is given (the override then applies until it is cleared). Because a store that is on the list and has been brought back must also be committed, the final log line says so (`list_updated: remove it in the same commit`).
- **Checks before writing (AC7):** all values come through `parseOverrideChange` (errors are listed together, nothing is written); the slug through `^[a-z0-9-]+$`; every text value through `sqlString`, every number through `sqlInt`. **Mutually exclusive options are refused** (`--hide` with `--unhide`; two modes at once; `--slug` with `--list`, `--export` or `--import`; no mode). An unknown option, a missing value, or `--local` with `--remote` is a usage error that writes nothing.
- **After the write** the command reads the store's override (and, for `--bring-back`, the store row) back and compares it with what it meant to write, as `hide.ts` does; it logs `override_done` (`target`, `slug`, the resulting fields **without the note**) and exits 0, or logs `override_not_applied` with what it found and exits 1. For `--clear` it checks the row is gone (clearing a store that has no override is not an error: it logs `override_none` and exits 0); for `--import` that the number of rows in the file are all in the database with equal values.
- **`--export`** reads every override joined to its store's slug (ordered by slug), checks the result with `parseOverridesFile`, and writes `docs/data/overrides.json` (an array, two-space indentation, a final newline), **replacing** the file. An empty database gives `[]`. It writes only the file, never the database.
- **`--import`** reads and validates `docs/data/overrides.json` with `parseOverridesFile` first, checks that **every slug exists in the database**, then upserts every row **with its saved `created_at`** (a restore must not change the times) in one SQL file, and checks the rows afterwards. It does not delete overrides that are not in the file.
- **`--list`** prints one line per override with the slug, the fields and `active` or `expired` (decided with the same rule as the site). Read-only.
- **Free-tier note (coding standards):** a handful of rows written once; nothing runs on a schedule. [Source: architecture/core-workflows.md#operator-override; architecture/coding-standards.md#critical-fullstack-rules; docs/stories/3.9.story.md (the command pattern)]

### Gaps and decisions for the developer to note

1. **The freshness change (Task 2) is confirmed.** **PO ruling 2026-10-30:** an active override keeps its store fresh for as long as it is active. The operator who sets an override is vouching for the store, so the command warns when no `--expires` is given and the README recommends always setting one (a month at most), because an override with no expiry keeps a store on the site until it is cleared.

5. **`--hide` is the override hide, not `is_visible`** (AC1): the pipeline keeps fetching the store. To stop fetching a blocking store use Story 3.9's `ops:hide`; to show one again with manual values use `--bring-back`.

9. **The note** is free text typed by the operator and is kept in the export file; the command does not log it.
